## F1. Go impact misses consumers of promoted embedded-struct methods

Severity: med.

Repro:
```sh
sh dogfood-7/findings/repro-app028-1/run.sh
```

The standalone Go fixture has `Shell struct { Gauge }`, `NewShell` in
`internal/model/shell.go`, and `(*Gauge).Value` in a separate annotated
`gauge_methods.go`. `client.Value` calls `model.NewShell().Value()`.
Both packages' tests pass with the method returning 7.

Actual: `impact CODE-BASE-001 --json` reports only `gauge_test.go`, with empty
`otherReqs`; it omits `client/client.go`, `client/client_test.go`, and
`REQ-CLIENT-001`. In contrast, querying `internal/model/shell.go` reaches both
client files. Changing only the embedded method's return from 7 to 8 was
verified to fail **both** package tests while the impact result still omitted
the client. The fixture was restored to 7 afterward.

Expected: follow method promotion through anonymous embedded fields so the
receiver implementation's change reaches its real callers and their tests,
or conservatively retain the imported package files when receiver promotion
cannot be resolved.

Location: `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:2805–2823`,
Go import-graph `goTypes`/`goRecv`/`narrow`. The initial imported-symbol hit
is `NewShell`/`Shell`; receiver expansion considers only types declared by
that hit. It does not follow the embedded `Gauge` type to its method file.
This is distinct from dogfood-6's direct methods-only receiver bug: the
imported outer type and method receiver here are **different**, linked by
Go's language-defined promotion.

Workaround: query the embedding/constructor file in addition to the receiver
file, and run the full gate. Do not rely on the missing cross-feature hint.

## F2. Go external-package stubs use the directory name instead of the declared package name

Severity: med.

Repro:
```sh
sh dogfood-7/findings/repro-app028-2/run.sh
```

The fixture already has `internal/runtimev1/existing.go` declaring
`package runtime`. Its external test explicitly imports that path as `rt`
and calls the not-yet-implemented `rt.NewGauge().Value()`. This is a legal
Go layout: import path and package identifier need not match.

Actual: `tdd stub TEST-GAUGE-001` creates
`internal/runtimev1/runtimev1_stub.go` with **`package runtimev1`**, alongside
the real file declaring `runtime`. Go then fails with
`found packages runtime (existing.go) and runtimev1 (runtimev1_stub.go)`.
The compile-check warning is honest, but the generated package is invalid
and the mixed-package error prevents the next method-inference probe.
The existing production file remains untouched.

Expected: infer the existing non-test Go package declaration and render the
stub with `package runtime`, regardless of the path tail or import alias.
Directory-name fallback is appropriate only when creating a new package.

Location: `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:925–947`,
`stubGo` external-package branch. `last = importPath.split('/').pop()` is
used by `render()` as `package ${e.last}` even when `hasGo` is true.

Workaround: hand-write a typed stub in the existing package, or change the
generated package declaration and add any uninferred behavior methods by
hand before recording Red. Do not rename real packages to fit the generator.
