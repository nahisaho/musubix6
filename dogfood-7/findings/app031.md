## F1. Go impact misses subpackage imports through a local replacement with a different module path

**Repro:** `bash dogfood-7/findings/repro-app031-3/reproduce.sh`
The fixture root requires `imported.local/sdk`, replaced by `./libs/shared`, whose `go.mod` declares `original.local/sdk`. The consumer imports the **subpackage** `imported.local/sdk/counter`; both modules' tests pass.

**Actual:** `impact REQ-LIB-001 --json` reports only `libs/shared/counter/counter_test.go` in `reachedFiles` and `otherReqs: []`. It omits the actual `consumer/consumer.go` caller and `REQ-APP-001`.

**Expected:** Resolve the local `replace` alias used by the importing module, follow the imported counter subpackage, and include its consumer implementation/test and cross-feature requirement. This is not the previously reported module-root-package exclusion: the import ends in `/counter`, and no package lives at the replaced module root.

**Location:** `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:2813-2820`, `importRev()` Go branch: `goMods`/`goModDir()` match only declared module paths and directory suffixes, without resolving `require` + local `replace` aliases.

**Workaround:** Manually inspect consumers, add explicit project `dependsOn` entries, and run full gates. Where feasible, align the local module declaration with the path used by the importer.

**Severity:** med — dependency/impact analysis silently omits a real, compiling cross-feature consumer.

## F2. Go TestMain suite-setup exits are accepted as strong assertion Reds

**Repro:** `bash dogfood-7/findings/repro-app031-4/reproduce.sh`
The annotated test genuinely fails (`Count()` returns 0, the assertion requires 1). `TestMain` has a configurable suite-setup early exit before `m.Run()`.

**Actual:** With `PROBE_SETUP_EXIT=1`, `tdd red TEST-PROBE-001` exits 0 and writes a strong Red (`exit: 1`, no `weak` field), reporting `fails with: FAIL`, although the selected test never ran. With setup exit 0, Green and the full gate also exit 0, without changing any implementation or assertion. Running normally then executes the selected test and fails `counter is not one`.

**Expected:** A suite-setup failure before the selected test executes must not establish strong assertion-Red evidence. Reject the unknown/unexecuted result (and reject Green without a selected test result), using Go test JSON or explicit target execution markers. This does not use `t.Skip`, TODO tests, a runner crash, or import/helper edits: the defect is attribution of a package-level suite-setup exit to the requested test.

**Location:** `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:690` (`RAN_TESTS` treats a timed Go package summary as execution), and `cmdTdd():2173-2200` (`zero`/Red validation allow a nonzero setup exit lacking any actual test result).

**Workaround:** Keep standard `TestMain` behavior (`os.Exit(m.Run())`) and separately validate setup. Use an explicit runner with `go test -json -count=1` that requires a result for the selected test; `--expect` with a unique assertion message also prevents accepting this particular setup Red.

**Severity:** high — unrelated setup exits can manufacture a strong Red→Green chain and full PASS for unchanged, failing code.
