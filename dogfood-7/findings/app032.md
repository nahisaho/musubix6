## F1. Go subtest Red can be attributed to a failing unannotated sibling

**Repro:** The complete fixture is `dogfood-7/findings/repro-app032-subtest/`.
`Add` is already correct. The annotated `t.Run("TEST_TABLE_001", ...)`
passes; only `t.Run("unrelated", ...)` fails. The enclosing test function
uses the documented `TestTEST_TABLE_001` naming convention.

```sh
cd dogfood-7/findings/repro-app032-subtest
S="$PWD/../../../.github/skills/lean-sdd-tdd/scripts/sdd.mjs"; node "$S" --root "$PWD" init
go test -v ./... -run '^TestTEST_TABLE_001$/^TEST_TABLE_001$'
node "$S" --root "$PWD" tdd red TEST-TABLE-001
```

**Actual:** The precise Go filter reports `PASS` for the annotated subtest.
The SDD command nevertheless prints `RED ok TEST-TABLE-001` and writes
strong Red evidence to `.sdd/tdd.jsonl`, citing the failed parent test.
The generated filter `TEST_TABLE_001(_|$)` selects the parent and runs
its unannotated sibling as well. No assertion in the annotated target fails.

**Expected:** Red must be attributed to the annotated subtest's own failure.
The runner must select the hierarchical `parent/subtest` name or reject
an unrelated sibling/parent failure, rather than establishing a strong Red
for an already-passing target.

**Location:** `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:421`
(`detectConfig` Go `testCmd`), `:2150` (`cmdTdd` command substitution),
and `:2173`/subsequent Red verdict handling. `RAN_TESTS` at `:690`
establishes only that some Go test ran, not that the annotated subtest failed.

**Workaround:** Use one annotated top-level Go function per TEST ID, or
configure the fixture's `testCmd` with
`["go","test","./...","-run","^TestTEST_TABLE_001$/^{IDU}$"]`.
An own-assertion-specific `--expect` is an additional wrong-reason guard.

**Severity:** high — unrelated failing subtests can supply mandatory
assertion-Red evidence for already-passing behavior.

## F2. Go impact omits methods declared on a local type alias

**Repro:** The complete fixture is `dogfood-7/findings/repro-app032-alias/`.
`type Alias = Base` is a local Go type alias, not an import alias or a
distinct embedded type. The method `func (Alias) Count() int` is also a
method of `Base`. The consumer imports `model.Base`, not `model.Alias`.

```sh
cd dogfood-7/findings/repro-app032-alias
S="$PWD/../../../.github/skills/lean-sdd-tdd/scripts/sdd.mjs"; node "$S" --root "$PWD" init
go test ./...
node "$S" --root "$PWD" impact CODE-METHOD-001 --json
```

**Actual:** `reachedFiles` and `reachedTests` contain only
`model/alias_test.go`; `otherReqs` is empty. `client/client.go`,
`client/client_test.go`, `TEST-CONSUMER-001` and `REQ-CONSUMER-001`
are omitted. Changing only the aliased receiver method's `return 7` to
`return 8` makes `go test ./client` fail, while impact still reports the
same empty cross-feature set. The fixture was restored to `return 7`
and both packages pass.

**Expected:** Alias receiver methods must be associated with the canonical
underlying local type, so consumers of `Base.Count` are included in impact.
Unlike the separately reported embedded-struct case, these are literally
the same Go type and method set, without embedding or method promotion.

**Location:** `.github/skills/lean-sdd-tdd/scripts/sdd.mjs:2804–2812`,
Go `goTypes`/`goRecv`/`narrow`: receiver names are compared literally;
local `type Alias = Base` declarations are not resolved.

**Workaround:** Query impact for both the method file and the canonical
type declaration file (`model/base.go`), and run the full Go suite/full
gate rather than trusting the narrowed cross-feature list.

**Severity:** med — false-negative impact can omit real cross-feature
consumers when planning verification after a method implementation change.
