# 第4編: 再試行を再現できる Webhook リレーを開発する

時計・乱数・送信・待機を差し替えられる Webhook リレーを、日本語の依頼から作ります。
失敗後の再試行と送信断念を、実時間の待機や外部 Webhook に依存せず検査します。

対象は、[第1編](tutorial-app-development-1.md) の SDD/TDD と、Promise の基本を理解した読者です。
musubix6 0.2.0、Node.js 24.21.0 で2026年10月22日に再実装した結果を反映しています。

## この編で作るものと完成条件

`webhook-relay` は、購読先へイベントを配送する学習用のライブラリーです。
今回作ったものには、本番用の HTTP 送信アダプターは含まれていません。
テストとデモの送信先は、注入した模擬 transport です。

| 機能 | 確認する条件 |
|---|---|
| 署名 | 本文の生バイト列と時刻から HMAC-SHA256 を計算する |
| 購読管理 | 公開する情報に秘密値を含めず、参照から内部状態を変更できない |
| 冪等キー | 同じキーの再受付と、有効期限・容量の境界を区別する |
| 再試行 | 応答と試行回数の表に従って、再送・成功・断念を決める |
| deadletter | 送信を断念したイベントを、成功とは別の状態で残す |
| 再現性 | 同じ注入条件から、別プロセスでも同じ実行トレースを得る |

ここでいう「注入」は、外部との境界を引数で渡すことです。
例えば `transport.send(request)` を模擬実装へ差し替えれば、503を3回返してから200にする状況を作れます。

入力プロンプトは、実際の指示を短縮・一般化した読者向けの例です。逐語録ではありません。
以下の成功・失敗や件数は実測値で、読者の生成物が同じテスト数になるとは限りません。

## 前提条件と今回の実験環境

Linux、Git、Copilot CLI、Node.js 24 を使います。
musubix6 0.2.0 と ESLint 9.39.5 は開発用依存へ完全固定し、実行時の外部 npm 依存は使いません。
開発は GPT-6.1 Sol、独立レビューは Claude Sonnet 5.5 です。
コンテナー工程は WSL と `wslc.exe` 3.0.4.0、公式 `node:24-alpine` で行いました。

今回はダミーの本文・秘密値だけを使い、`approval: auto` と AI の独立レビューで進めています。
人間承認を受けた記録ではありません。外部への実送信や実際の秘密情報は扱いません。

新しいディレクトリで Copilot CLI を起動します。

```sh
mkdir -p /tmp/musubix6-reader/webhook-relay
cd /tmp/musubix6-reader/webhook-relay

```

### 入力プロンプト: 実験用の環境を初期化する

```text
webhook-relay 用の新しい Git リポジトリを準備してください。
Node.js 24 の ESM とし、実行時は Node 組込みとローカルモジュールだけを使います。
開発用の musubix6 0.2.0 と ESLint 9.39.5 は完全固定してください。

コピーしたスキルや生成ログは混ぜず、全テストと lint を gate へ設定してください。

```

準備後は同じディレクトリでセッションを開き直します。

## 時計・乱数・送信・待機の契約を先に決める

### 入力プロンプト: 外部との境界を仕様にする

```text
ローカルで検査できる Webhook リレーを作ってください。
まず .sdd/plan.md に機能と依存を定め、
backoff、signature、subscribers、idempotency、delivery、
retry-deadletter、relay の仕様を .sdd/specs/<feature>.md に作ってください。

時計 clock.now()、乱数 rng()、送信 transport.send(request)、
待機 scheduler.wait(ms) を外から渡す設計にしてください。
send と wait の同期・非同期、例外、不正な戻り値も契約へ含めてください。
テストの期待値を、実装が返した値から作らないでください。

REQ/TEST ID、PASS 条件、具体的な反例、正常対照・境界・エラーを記載してください。
契約、信頼する入力、実行、判定、証跡履歴、統合・配布を点検してください。
有限の配送状態と応答方針を表にし、許可・禁止の両方を確認してください。
実際の HTTP、DNS、SSRF 対策、永続化、実データは対象外にしてください。
```

実行結果を固定するには、時計だけでなく乱数と待機も管理する必要があります。
今回の再現性テストでは、アプリの import 前にグローバルの `Date` と `Math.random` を使えなくした条件でも確認しました。
注入を宣言しているだけで、内部では実時間を使う実装を見逃さないためです。

## 署名・冪等キー・再試行の役割を分ける

署名は本文と時刻の認証、冪等キーは同じ要求の扱い、再試行は配送の進め方を決めます。
どれか1つがあれば、他の問題も解決するわけではありません。

| 条件 | 反例 | 確認内容 |
|---|---|---|
| 署名が生バイト列へ結びつく | JSON を再整形して検証する | 本文を1バイト変えた署名の拒否 |
| 購読情報を安全に返す | 公開情報から秘密値や内部参照が漏れる | 戻り値と内部状態の独立性 |
| TTL 境界を仕様どおり扱う | 有効期限と等しい時点を有効扱いする | 境界の直前・同値・直後 |
| 正常な配送を受け付ける | 重複防止のため全件を拒否する | 新しいキーの正常対照 |
| 断念を成功にしない | 試行上限で `delivered` にする | 送信回数と終端状態 |

### 入力プロンプト: タイムアウトと同時実行も設計する

```text
購読先ごとの FIFO と、異なる購読先の独立性を定義してください。
送信中の解除・再登録、タイムアウトと実送信 Promise の完了順序も仕様にしてください。
タイムアウトで abort を通知しても、実送信が終わる前に同じ購読先へ重複送信しない設計にしてください。
応答しない transport がある場合の限界を明記し、完了したふりをしないでください。

署名、秘密値の公開範囲、冪等キーの容量、再試行状態、検査用オラクルを
Claude Sonnet 5.5 の独立レビューで確認してください。
指摘と処置、隔離した成立性検証の結果を仕様へ残してください。
```

今回の配送方針は30セルを確認し、HTTP 数値ステータスについては500個を確認しました。
これは決めた表の検査であり、実ネットワークや任意の負荷を網羅した結果ではありません。

## 本当に失敗する Red を確認してから実装する

### 入力プロンプト: 証跡を区別して実装する

```text
各機能で、正常対照と反例のテストを先に書いてください。
読めるスタブの誤った戻り値や拒否不足を assertion で検出し、
実際の Red を確認してから実装してください。
TypeError、import/setup 失敗、skip を Red の代わりに使わないでください。

実装後は Green、独立レビュー、失敗機構ごとの限定 mutation を確認してください。
mutation の検出理由とハッシュを記録し、元のバイト列へ戻して影響する検査を再実行してください。
生き残った mutation や、期待した理由で落ちなかった試行は検出成功へ数えないでください。
実装後に追加した回帰は、当初の実装前 Red と区別してください。

全体 gate と JavaScript 診断を実行し、
.experiment/result-native.json に成功・失敗・未確認を分けて保存してください。
```

最初に作った relay の Red 4件は TypeError だったため、今回の証跡として採用しませんでした。
本体の実装前に、誤った戻り値を assertion で検出するテストへ直して実行しています。
後から見つかったキャンセルや世代管理などの不具合には、別の回帰 Red/Green を記録しました。

ネイティブ工程は最終的に18要件・19テストとなり、全体 gate と JavaScript 診断が PASS でした。
mutation の記録43件のうち、期待した検出として計上したのは38件です。
生き残り、意図しない失敗、不完全な試行の5件は数えず、履歴に残しています。

レビューで一度報告された署名の一時的な不一致は、原因を特定できていません。
後続のレビューと、親セッションを静止状態にした確認は成功しました。
ただし、不一致の原因を解明したわけではありません。
同じ条件でも結果が変わる非決定性の有無も、この記録だけでは断定できません。

## 固定条件で再試行と deadletter を実行する

### 入力プロンプト: 2つの配送シナリオを動かす

```text
examples/demo.mjs に、固定した時計・乱数・模擬送信・模擬待機のデモを作ってください。
1つ目は503を3回返してから200、2つ目は常に503で最大5回としてください。
デモの期待値は、実装とは別の契約 fixture に先に固定してください。
送信回数、待機列、終端状態と、注入した時刻を含むトレースを比較してください。
新しい別プロセスで繰り返し、出力のバイト列が一致することも確認してください。
外部 Webhook へは送信せず、実時間の待機で再試行を検査しないでください。
```

今回の結果は次のとおりです。

| シナリオ | 送信回数 | 待機列、ミリ秒 | 終端状態 | 注入時計の最終時刻 |
|---|---:|---|---|---:|
| 503を3回、その後200 | 4 | `[100,200,400]` | `delivered` | 700 |
| 常に503、最大5回 | 5 | `[100,200,400,800]` | `dead` | 1500 |

この700・1500は注入した時計の値で、テストにかかった実時間ではありません。
トレースは `relay.trace()` から取り出し、デモが固定値の成功メッセージを返すだけにならないよう検査しました。

## 同じデモをネットワークなしの WSL コンテナーで確かめる

### 入力プロンプト: 環境を変えても結果を比較する

```text
wslc-containers を使い、公式 node:24-alpine から実行用とテスト用のイメージを作ってください。
実行用に開発ツールやテストを入れず、テスト用には必要な全 fixture を含めてください。
ネットワークは none、ポート公開なしで実行してください。

全アプリテストを実行し、数・終了コード・skip を確認してください。
元の注入ポートを使うデモを新しいプロセスで2回実行し、
契約 fixture、ネイティブ実行、コンテナー内の繰返しのそれぞれと比較してください。
子プロセスのエラー、signal、非ゼロ終了、不一致を成功へ変換しないでください。

自分が作ったリソースだけを片づけ、
ネイティブの全体 gate と JavaScript 診断も再実行してください。
```

コンテナー工程の追加検査を含め、最終的に19要件・21テストになりました。
コンテナー内の21件はすべて成功し、skip は0件でした。
ネイティブとコンテナー、それぞれの繰返しでデモの出力がバイト単位で一致しています。
出力から計算した SHA256 は、今回は次の値でした。

```text
36c45c419bd1a8b18cb4e91a8e9e31acc993b03f2676834a5161e997536cc48c
```

このハッシュは今回の実装・出力形式に対する値です。読者が別の形式を生成した場合の汎用期待値ではありません。
出力をこの値へ合わせるために実装や判定を変更してはいけません。

最初の集計器は TAP と配列 JSON を仮定していましたが、実出力は spec reporter と NDJSON でした。
テスト21件の成功とは別に、集計工程は失敗しています。
失敗した記録を残し、集計器を直してデモを含む一連の検証を実行し直しました。
gate や再試行の方針を弱めて通したわけではありません。

## つまずきと対処・未確認の範囲

| 症状 | 原因・確認点 | 対処 |
|---|---|---|
| 同じテストで待機列が変わる | 時計・乱数・待機の一部が実環境へ依存する | すべての境界を注入し、別プロセスで比較する |
| テストが落ちるが Red として使えない | TypeError や読込み失敗で assertion に届いていない | 実装前に、期待した失敗理由へ直す |
| タイムアウト後も完了しない | 実送信 Promise が終了していない | 未完了を報告し、成功を返す回避を入れない |
| 同じ本文なのに署名が違う | 生バイト列や時刻の差の有無を確認する | 文字列化・再整形前の本文と注入時刻を比較する |
| テスト成功なのに集計できない | reporter や JSON の出力形式が想定と異なる | 生出力を保持して集計器を訂正する |

署名だけでは、許容時刻内のリプレイを防げません。
上の表は一般的な切り分け方法であり、今回の未解明な署名不一致の原因を示すものではありません。
状態はメモリー上だけにあり、永続的な exactly-once 配送も保証しません。
応答しない transport・scheduler がある場合の進行保証は未確認です。
実 HTTP、DNS/SSRF 対策、実秘密値を使う運用、負荷性能も未確認です。
