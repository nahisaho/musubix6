# チュートリアル 4: 時間と再試行を、決定的に開発する(Webhook 配信ライブラリ)

[チュートリアル 2](tutorial-app-development-2.md) では、状態遷移のある HTTP API を、複数機能に分けて開発しました。このチュートリアルでは、実行のたびに結果が変わりうる振る舞いを、テストで確実に確かめる方法を扱います。対象は、**時刻、乱数、非同期の送信**です。

| | チュートリアル 2 | このチュートリアル |
|---|---|---|
| 題材 | 在庫つきの注文受付 HTTP API | Webhook 配信ライブラリ(購読者、再試行、デッドレター、冪等キー、HMAC 署名) |
| 規模 | 5 機能(REQ 46 件) | **7 機能**(REQ 78 件、テスト 80 件) |
| 区分 | T2 が中心 | T1 が 2 機能、**T2 が 5 機能** |
| 難所 | 在庫の原子性、状態遷移 | **時刻、乱数、待ち時間、並行する送信**(結果が毎回変わりうる) |
| 新しく使うもの | `plan`、`## Design`、並列レビュー | **注入口(テスト用の接合点)の設計**、時刻を指定した具体例の要件、**30 セルの状態遷移表**、前の機能の spec の再承認 |
| 後半の作業 | キャンセルと在庫の戻し | 再試行とデッドレター、公開の入口、決定性の結合テスト |

ここに載せたプロンプトと結果は、`/tmp/musubix6-tutorial-4/webhook-relay` で実際に開発したときの記録です(Node.js 24、Copilot CLI)。

## 2. 機能に分割する:時間と乱数の「注入口」を決める

時間に依存する機能は、**最初に、外から差し込む部品(注入口)を決める**のが重要です。ここを決めずに作ると、実装が `Date.now()` や `Math.random()` を直接呼び、テストに本物の待ち時間が必要になります。

### 入力プロンプト

```text
Webhook 配信サービスのライブラリを作りたい。購読者(URL と署名用の秘密鍵を持つ)を登録し、イベントを発行すると、購読者ごとに HTTP で配信する。配信が失敗したら、指数バックオフとジッターで間隔をあけて再試行し、最大回数を超えたらデッドレターに入れる。同じ冪等キーのイベントは 1 回だけ配信し、購読者ごとの配信順序を守り、ペイロードには HMAC 署名を付ける。
時刻と送信処理は外から差し込めるようにして、テストでは本物の待ち時間(sleep)や乱数に頼らず、決定的に確かめたい。
機能が多いので、機能に分割して、作る順序と依存関係を決めて。そのあと、最初の機能の要件定義書を作って。時刻や乱数のように結果が毎回変わりうる振る舞いは、テストで確かめられる形で要件に書いて。ヒアリングは「おまかせ」で推奨値にして。
```

結果の `.sdd/plan.md` です。

```md
| order | feature | depends | note |
| --- | --- | --- | --- |
| 1 | backoff | - | 純粋関数。rng を注入して指数バックオフ+ジッターの待ち時間を算出。sleep しない |
| 2 | signature | - | HMAC-SHA256 署名と検証(定数時間比較)。T2 |
| 3 | subscribers | - | 購読者の登録・取得・削除(URL 検証、秘密鍵) |
| 4 | idempotency | - | 冪等キーの重複排除(同一キーは 1 回だけ受理) |
| 5 | delivery | signature, subscribers, idempotency | 発行→購読者ごとの FIFO キュー→注入 transport で送信。T2 |
| 6 | retry-deadletter | backoff, delivery | 失敗時の再試行(注入 clock/scheduler)、上限超過でデッドレター。T2 |
| 7 | relay | retry-deadletter | 公開ファサード(publish/subscribe/deadLetters)と結合テスト |
```

plan には、次の 1 行も書かれました。これが、このライブラリの**テスト用の接合点(test seam)**です。

```text
注入ポート: clock.now(), rng()(0以上1未満), transport.send(req), scheduler.wait(ms)。
実時間 sleep と Math.random はテストで使わない。
```

| 注入口 | 本番での実体 | テストでの実体 |
|---|---|---|
| `clock.now()` | `Date.now()` | 固定値、または手で進める時計 |
| `rng()` | `Math.random` | 固定値の列(0.5、0.25 など) |
| `transport.send(req)` | `fetch` による HTTP 送信 | 状態コードを決めて返す偽の送信処理 |
| `scheduler.wait(ms)` | `setTimeout` | 呼ばれた時間を記録して、すぐ解決する偽物 |

この分割では、時間に依存しない純粋な部品(`backoff`、`signature`)を先に作り、時間と並行性が絡む `delivery`、`retry-deadletter` を後にしています。

### 時間と非決定性を EARS で書く

最初の機能 `backoff` から、要件を 1 つ引用します。時間、乱数、待ち時間を、**「何に依存するか」「具体的な数値」**として書いている点に注目してください。

```md
| REQ-BACKOFF-001 | When createBackoff({baseMs, factor, capMs, maxAttempts, jitter:'none'}).delayMs(n) is called,
  the system shall return floor(min(capMs, baseMs*factor^(n-1)))
  (例: base=100, factor=2, cap=1000 → n=1..5 で 100, 200, 400, 800, 1000). |
```

非決定的な振る舞いを要件に書くときの型は、次の 4 つです。

| 型 | 書き方 | 例 |
|---|---|---|
| 入力の固定 | 変わりうる値を、注入口の入力として明示する | 「rng が 0.5、0.25 の順に返すとき」 |
| 具体例 | 開始時刻と期待値を数値で書く | 「clock が t=1000 のとき、1 回目の失敗の待ち時間は 100 ms」 |
| 呼び出し回数 | 注入口を何回呼ぶかを決める | 「rng は、再試行ごとにちょうど 1 回呼ぶ(`jitter='none'` では 0 回)」 |
| 禁止 | 直接の読み取りを禁止する | 「注入した rng がある場合は `Math.random` を読まない」 |

`backoff` の独立レビューでは、禁止の型について、次の Blocking の指摘が出ました。

- `REQ-BACKOFF-004` 「`Math.random` を読まない」は、「省略時は `Math.random` を既定の rng にする」という前提と矛盾する。

要件に書くと、こうした矛盾が実装の前に見つかります。

## 3. T1 の機能を、独立レビューつきで進める(backoff)

### 入力プロンプト

```text
.sdd/plan.md の次の機能に進んで。要件定義書がすでにあれば、別のエージェントで独立レビューして指摘を反映し、承認して。そのあと実装して(先に全テストを書いて Red を確認してから Green にして)、全体の gate を通して、コミットして。時刻や乱数に依存する振る舞いは、本物の待ち時間や Math.random を使わずにテストして。
```

独立レビューは Blocking が 3 件でした。

| 場所 | 指摘 | 対応 |
|---|---|---|
| REQ-BACKOFF-004 | 「`Math.random` を読まない」と「省略時は既定の rng」が矛盾する | 注入した rng があれば読まない。省略時のみ、作成時に既定の rng を使う |
| REQ-BACKOFF-006 | `factor` に `Infinity` や `NaN` が通る | 1 以上の有限数に限る |
| REQ-BACKOFF-001 | 入力が小数でも許されるのに、戻り値は整数 ms とされている | 全ジッターモードで、最終値を切り捨てる |

Non-Blocking の指摘も 2 件反映されました。`delayMs(n)` の `n` は「失敗済みの回数」であること、乱数は、すべての入力の検証が済んでから 1 回だけ呼ぶことです。

```text
SDD GATE PASS
✓ trace: 8 REQ, 0 errors
✓ ledger: 18 entries, chain intact
✓ tdd evidence: 9/9 tests Red→Green
```

テストでは、`Math.random` と `Date.now` を、**呼ばれたら例外を投げる偽物に差し替える**手法が使われました。注入口を通さずに実時間や乱数に触れると、テストが失敗します。「使っていない」ことを、コードの目視ではなく、テストで確かめられます。

## 4. T2 の機能を、観点別の並列レビューで進める(signature)

署名の検証は、セキュリティに関わります。さらに、署名に含めるタイムスタンプと許容時間は、時刻に依存します。

### 入力プロンプト

```text
.sdd/plan.md の次の機能に進んで。署名の検証は、比較の仕方や再送(リプレイ)の扱いなど、セキュリティに関わるので慎重に進めたい。時刻に依存する部分(署名に含めるタイムスタンプと許容時間)は、時計を外から差し込める形で、テストで確かめられるように要件に書いて。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。そのあと実装して(先に全テストを書いて Red を確認してから Green にして)、全体の gate を通して、コミットして。
```

セキュリティ、正しさ、契約、テストの 4 観点で並列にレビューされ、Blocking が 4 件出ました。時間に関わるものを挙げます。

| 観点 | 指摘 | 対応 |
|---|---|---|
| 正しさ | 注入した時計が 0〜999 ms を返すと、`t=0` の署名ができる。検証側は `t` を正の整数と定義していて、**自分で作った署名を検証できない** | `t` を非負の整数にする |
| セキュリティ | 時計が巨大な値や `Infinity` を返すと、桁あふれや不正なヘッダーができる | 時計の値を非負の安全な整数に限る |
| 正しさ | 不正なヘッダーと壊れた時計が同時にあるとき、どのエラーが優先されるか不明 | 検証の優先順位を要件に明記する |
| セキュリティ | 許容時間内の完全な再送は、署名だけでは防げない | この機能では防がない。`idempotency` での重複排除を前提にして、文書に明記する |

```text
SDD GATE PASS
✓ lock signature: ok [ai, review file]
✓ trace: 18 REQ, 0 errors
✓ tdd evidence: 19/19 tests Red→Green, 2 weak Red — … TEST-SIGNATURE-004, TEST-SIGNATURE-010
```

`weak Red` の 2 件は、失敗の原因が「スタブの未実装」で、検証したい振る舞いそのものではなかったという記録です。gate は通りますが、以降の gate でも警告として残ります。

> **つまずいた点: 並列エージェントの出力が混ざった**
> このときの実行ログには、並列レビューの出力が文字単位で混ざった箇所がありました。ログは読みにくくなりますが、結果の `.sdd/review-signature.md` と gate は正常でした。**判断は、ログではなく、成果物と gate で行ってください。**

## 6. 状態機械を、すべての組み合わせで数え上げる(delivery)

この機能が、今回の中心です。1 件の配信は、次の状態を持ちます。

| 状態 | 意味 |
|---|---|
| pending | 送信待ち |
| in-flight | 送信中(購読者ごとに、同時に 1 件だけ) |
| delivered | 配信済み(終端) |
| failed | 失敗した。再試行か、あきらめるかの判断待ち |
| dead | あきらめた、または取り消された(終端) |

### 入力プロンプト

```text
.sdd/plan.md の次の機能に進んで。1 件の配信は pending / in-flight / delivered / failed / dead の状態を持つ状態機械なので、「状態 × イベント」の組み合わせをすべて数え上げて、許される遷移と許されない遷移を、どちらも要件にして(retry-deadletter で扱う遷移も、この機能での扱いを明記して)。購読者ごとの配信順序と、送信処理(transport)の注入、署名の付与、冪等キーの重複排除は、時刻や並行実行に依存するので、テストで確かめられる形で要件に書いて。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。そのあと実装して(先に全テストを書いて Red を確認してから Green にして)、全体の gate を通して、コミットして。
```

### 状態 × イベントの 30 セル

spec の先頭に、5 状態 × 6 イベントの表ができました。許される遷移は 7 セル、禁止は 23 セルです。

| 状態＼イベント | dispatch | succeed | fail | retry | giveUp | cancel |
|---|---|---|---|---|---|---|
| pending | →in-flight | ✗ | ✗ | ✗ | ✗ | →dead |
| in-flight | ✗ | →delivered | →failed | ✗ | ✗ | ✗(保留) |
| delivered | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| failed | ✗ | ✗ | ✗ | →pending | →dead | →dead |
| dead | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

イベントは、次の 6 つです。

- `dispatch`: 送信の開始
- `succeed`: 2xx の受信
- `fail`: 失敗の確定
- `retry`: 再試行の準備
- `giveUp`: あきらめる
- `cancel`: 購読者の削除による取り消し

要件は、この表を**唯一の正**にしています。

- `REQ-DELIVERY-001`: `nextState(state, event)` が、30 セルすべてについて、許可なら遷移先を、禁止なら `undefined` を返す。すべての遷移は、この関数だけを通る。
- `REQ-DELIVERY-002`: 禁止のセルにイベントが来たら、`{ok:false, reason:'illegal_transition'}` を返し、状態、試行回数、履歴を変えない。遅れて届いた送信結果は、無視する。

テストは、30 セルを**全件走査**します。「列挙したつもり」の漏れが、コードで検出されます。

#### in-flight × cancel を「禁止」にした理由

`in-flight` 中に購読者を削除すると、送信が途中で止まります。並列レビューの指摘から、「送信中の配信は取り消さず、完了させる。ただし、完了後は再試行しない」という扱いになりました。つまり `in-flight × cancel` は、遷移させず**保留**します(表の「✗(保留)」)。

### 時間と並行に関する Blocking の指摘

並列レビューでは、Blocking が 10 件出ました。時間と並行に関わるものを挙げます。

| 観点 | 指摘 | 対応 |
|---|---|---|
| 時間 | 送信の完了と、タイムアウトが**同じ時刻**に起きたとき、どちらが勝つか不明で、決定的なテストが書けない | 先に登録された `scheduler.wait` が勝つ。遅れた応答は無視する |
| 並行 | 送信処理が、同じ `delivery` を再入して呼ぶと、状態がずれる | 状態を `in-flight` にして、記録を登録してから `send` を呼ぶ。再入した処理は、外側の処理が終わるまで保留する |
| 並行 | `scheduler.wait` が失敗(reject)したとき、`in-flight` のまま残り、キューが詰まる | 失敗として扱い、`failed` に遷移させる |
| 状態 | 購読者の削除後に `enqueue` すると、受理されたまま、送られない記録が残る | 削除済みの購読者への `enqueue` は拒否する |
| セキュリティ | 送信処理が、DNS の再束縛や転送(リダイレクト)で、内部のアドレスに接続しうる | 実際の送信処理の責務として、要件の対象外に明記する |
| セキュリティ | 本文の保持量に上限がなく、メモリを使い尽くせる | 保持するバイト数の上限を追加し、超えたら拒否する |

> **つまずいた点: 実行が時間の上限で止まった**
> この実行は、590 秒の上限に達して、終了コード 124 で止まりました。実装と gate は完了していましたが、**コミットされていませんでした**。同じセッションの再開はせず、新しいセッションで、次の依頼をしました。

#### 追加の依頼


## 7. 再試行とデッドレター(retry-deadletter)

この機能で、時刻、乱数、待ち時間が、すべてそろいます。

### 入力プロンプト

```text
.sdd/plan.md の次の機能に進んで。失敗した配信を、待ち時間をあけて自動で再試行し、最大回数を超えたらデッドレターに入れる機能なので、待ち時間を決める時計と乱数、待ち時間の経過(スケジューラ)は、すべて外から差し込める形にして、本物の待ち時間を使わないテストで確かめられるように要件に書いて。「何回目の失敗で、何ミリ秒後に再試行され、いつデッドレターになるか」を、時刻を指定した具体例で要件にして。状態の遷移は、すでにある状態機械の表を使って、この機能で新しく発生する遷移がないか数え上げて確かめて。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。そのあと実装して(先に全テストを書いて Red を確認してから Green にして)、全体の gate を通して、コミットして。
```

### 時刻を指定した具体例(spec より)

```md
## 具体例(時刻指定。baseMs=100, factor=2, capMs=1000, maxAttempts=3, jitter='none', minDelayMs=1、
   clock は t=1000 から、transport は常に status 500 を返す)
- maxAttempts=5, capMs=300: 失敗 1〜4 回目の wait は 100, 200, 300, 300 ms、5 回目の失敗で dead。
- jitter='full' で rng が 0.5, 0.25 の順: 1 回目 floor(0.5×100)=50ms、2 回目 floor(0.25×200)=50ms。
  rng=0 なら delayMs=0 だが minDelayMs=1 により wait(1)。
```

`rng=0` のときの扱いが、時間の要件の落とし穴です。ジッターの結果が 0 ms になると、待たずに再試行が続き、**即時のループ**になります。そこで、`minDelayMs`(既定 1 ms)という下限が加わりました。

主な要件は、次のとおりです。

- `REQ-RETRY-DEADLETTER-002`: 失敗して再試行すると決めたとき、`clock.now()`、`backoff.delayMs(n)`、`scheduler.wait(...)` を、**それぞれちょうど 1 回**呼ぶ。
- `REQ-RETRY-DEADLETTER-005`: 乱数は、注入した `rng` だけから取る。`Math.random` を既定にはしない。呼び出しは、再試行の予約ごとにちょうど 1 回(`jitter='none'` と、あきらめる場合は 0 回)。
- `REQ-RETRY-DEADLETTER-004`: 最大回数に達したら、待たずに `giveUp` して、デッドレターに記録する。
- `REQ-RETRY-DEADLETTER-012`: 再試行するのは、408、429、5xx、タイムアウト、通信エラーだけ。それ以外(404 など)は、最初の失敗で、デッドレターにする。

#### 新しい遷移が 0 件であることを確かめる

要件の `REQ-RETRY-DEADLETTER-001` は、`delivery` の 30 セルを走査して、**この機能が起こす遷移が `failed→pending` と `failed→dead` の 2 つだけ**であることを、テストで確認します。状態機械を拡張していない、という保証です。

### 前の機能の spec を直す(再承認)

並列レビューで、次の指摘が出ました。

> 失敗の検知を `idle()` の待ち合わせで行うと、別の購読者が送信中のとき、検知が遅れる。

そのため、`delivery` に任意の `onFailed` フックを足しました(`REQ-DELIVERY-017`)。**承認済みの spec を直したため、再レビューと再承認**が行われています。

- 追加の記録は、`.sdd/review-delivery-onfailed.md` です(既存の `review-delivery.md` は、そのままです)。
- フックは、`in-flight→failed` の直後に、1 回だけ呼ばれます。渡されるのは、`id`、`subscriberId`、`attempts`、`lastFailure` だけです。秘密鍵と本文は渡しません。
- 状態の表は、変わりません(新しい遷移は 0 件)。

```text
SDD GATE PASS
✓ lock delivery: ok [ai, review file]
✓ lock retry-deadletter: ok [ai, review file]
✓ trace: 64 REQ, 0 errors, 1 warnings
✓ tdd evidence: 65/65 tests Red→Green, 2 weak Red — …
```

## 8. 公開の入口と、決定性の結合テスト(relay)

最後の機能は、部品をつなぐ入口です。ここでは、**同じ入力で何度実行しても、同じ結果になること**を、要件にします。

### 入力プロンプト

```text
.sdd/plan.md の次の機能に進んで。これまでの部品をつないだ公開の入口(購読者の登録、イベントの発行、デッドレターの参照)を作る。購読者が複数いるときの、購読者ごとの順序、同じ冪等キーの重複排除、失敗からの再試行、デッドレターまでを、固定の時計・固定の乱数・偽の送信処理で、本物の待ち時間なしに通しで確かめる結合テストを、「時刻を指定した具体例」として要件に書いて。同じ入力で何度実行しても同じ結果になること(決定性)も要件にして。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。そのあと実装して(先に全テストを書いて Red を確認してから Green にして)、全体の gate を通して、コミットして。
```

開始時刻を `1700000000000` に固定した、3 つのシナリオが要件になりました。

| シナリオ | 内容 |
|---|---|
| S1 | 複数の購読者の順序、冪等キーの重複排除、503 を 3 回返してからの成功、デッドレターまでを、T0 から T0+2000 ms まで通しで確認する |
| S2 | 送信のタイムアウトからの再試行(応答が 10000 ms と 10001 ms の境界を含む) |
| S3 | 再試行できない失敗(400) |

決定性は、2 つの要件になっています。

- `REQ-RELAY-011`: 同じ入力で 2 回実行した、**時刻付きの記録(trace)が完全に一致する**。
- `REQ-RELAY-012`: 依存するモジュールも含め、実時間と乱数を、例外を投げる偽物に差し替えます。この状態で全シナリオを通す。

relay の独立レビューでは、Blocking が 7 件出ました。決定性に関わるものを挙げます。

| 指摘 | 対応 |
|---|---|
| 自動生成した秘密鍵は実乱数なので、署名が実行ごとに変わり、決定性が崩れる | 固定の秘密鍵か、固定の `randomBytes` を必須にする |
| 記録(trace)の項目、順序、確定の境界が未定義 | 正規のスキーマを定める。同じ期限のタイマーは、登録順に発火させる |
| `relay.mjs` だけを検査しても、他のモジュールへの委譲で、実時間の読み取りを回避できる | 依存するモジュールを含む、全体の実行を、偽物の下で行う |
| 購読解除の「以後、送信しない」は、送信中の配信を取り消さない仕様と矛盾する | 「新しい試行を始めない」に限定する。送信中のものは完了して、再試行しない |

```text
SDD GATE PASS
✓ lock relay: ok [ai, review file]
✓ trace: 78 REQ, 0 errors, 1 warnings
✓ ledger: 178 entries, chain intact
✓ tdd evidence: 79/79 tests Red→Green, 2 weak Red — …
```

### 確認と、確認していないこと

### 入力プロンプト


エージェントは、gate が PASS で、`npm test` が 80 件すべて成功したことを報告しました。そのうえで、次の指摘と、確認していないことを挙げています。

## 11. つまずいたときの依頼例

| 症状 | 原因 | 依頼の例 |
|---|---|---|
| 実行が終了コード 124 で止まった | 1 回の実行の時間の上限に達した | 「直前の作業が途中で止まったようなので、リポジトリの状態を確認して、残っていることがあれば完了して」 |
| テストに本物の待ち時間が入る | 実装が `setTimeout` や `Date.now` を直接呼んでいる | 「実時間と乱数を注入口に切り替えて、`Date` と `Math.random` が呼ばれたら失敗するテストを足して」 |
| 同じ時刻に 2 つの出来事が起きたときの挙動が決まらない | 要件に勝敗の規則がない | 「同じ時刻に起きたときの優先順位を要件にして、境界の値(10000 ms と 10001 ms など)でテストして」 |
| 状態の遷移に漏れがありそう | 組み合わせを数え上げていない | 「状態 × イベントの全組み合わせを表にして、禁止の遷移もすべて要件とテストにして」 |
| 前の機能の gate が `lock … stale` で失敗する | 承認済みの spec を直した | 「spec を直したので、再レビューして、再承認して」 |
| ログが読めないほど混ざっている | 並列のエージェントの出力が重なった | 「`gate` と `review check` の結果で、状態を報告して」 |
| コンテナーのビルドが `network is unreachable` で失敗する | コンテナーからレジストリに届かない | 「ローカルのイメージだけでビルドする方法に切り替えて」 |
