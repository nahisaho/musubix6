# 第5編: サービス間の契約変更を検証して進める

注文サービスとダミー決済サービスを別プロセスで作り、共通契約の変更を両側へ反映します。
変更の影響先、実際のテスト失敗、再試行と結果不明の違いを確認してから、2つのコンテナーを接続します。

対象は、[第2編](tutorial-app-development-2.md) の HTTP と、[第4編](tutorial-app-development-4.md) の再試行を理解した読者です。
musubix6 0.2.0、Node.js 24.21.0 で2026年10月22日に再実装した結果を反映しています。

## この編で作るものと完成条件

`shop-services` は、単一リポジトリ内の4プロジェクトで構成する学習用システムです。
決済はメモリー上のダミー処理で、実際の課金はしません。

| プロジェクト | 役割 |
|---|---|
| `contract` | 要求・応答の schema、固定 fixture、検証器 |
| `services/payments` | `POST /charges` を提供する側 |
| `services/orders` | `POST /orders` を受け付け、payments を呼ぶ側 |
| `integration` | 別プロセスの HTTP 接続、停止、契約変更の検査 |

完成条件は、正常な注文が `paid` になることだけではありません。
契約変更で4プロジェクトが検査対象になること、未対応側のテストが実際に失敗すること、決済サービスを止めた結果を成功と誤認しないことも確認します。

以下の入力プロンプトは、実際の指示を短縮・一般化した読者向けの例です。逐語録ではありません。
数値や成否は今回の実測値で、同じ文面から同じファイルやテスト数が必ず生成されるという意味ではありません。

## 前提条件と今回の実験環境

Linux、Git、Copilot CLI、Node.js 24 の ESM を使います。
アプリ実行時の外部 npm 依存はなく、musubix6 0.2.0 と ESLint 9.39.5 を開発用へ完全固定しました。
開発は GPT-6.1 Sol、独立レビューは Claude Sonnet 5.5 です。
コンテナー工程は WSL、`wslc.exe` 3.0.4.0、公式 `node:24-alpine` で確認しました。

今回の `approval: auto` は、ダミーデータのローカル実験に対する AI レビューの記録です。
人間承認、実決済の許可、公開の許可ではありません。
他のプロジェクトのプロセスや共有コンテナーには触れません。

```sh
cd /tmp/musubix6-reader/shop-services
```

```text
shop-services 用の新しい Git リポジトリを用意してください。

npx musubix6 init . --host copilot と npx musubix6 sdd init を使って初期化し、

trace と lint はこれらの実装・テストを含め、コピーしたスキルや生成ログは除外してください。
```

準備後は同じディレクトリでセッションを開き直します。

## 契約・提供側・利用側を仕様に分ける

### 入力プロンプト: ベースラインを定義する

```text
注文とダミー決済の2サービスを作ってください。
最初に .sdd/plan.md と機能別の .sdd/specs/<feature>.md を作り、
共通契約、決済処理、決済の冪等性、注文受付、決済クライアント、統合へ分けてください。

入力は orderId、amount、currency としてください。
payments の成功応答には入力の値、chargeId、status=succeeded を含めてください。
この段階では processedAt はまだ追加しません。
同じ Idempotency-Key と同じ内容の再要求は、同じ成功結果を返してください。
同じキーで違う内容は拒否し、同時要求でも処理を重複させないでください。

orders は決済の結果により paid、payment_declined、payment_failed、
payment_unconfirmed を区別してください。
通信失敗や不正な応答を、支払成功へ置き換えないでください。
再試行の対象、上限、待機、タイムアウト、容量の条件も表にしてください。

REQ/TEST ID、PASS 条件、具体的な反例、正常対照・境界・エラーを記録してください。
契約、信頼する入力、実行、判定、証跡履歴、統合・配布を点検してください。
採用する JSON Schema の機能だけを明記し、汎用の完全実装とは説明しないでください。
```

今回のベースラインは6機能・19要件・22テストでした。
schema の検証器は採用した部分集合だけを扱い、JSON Schema 全体への対応ではありません。

## 結果不明と再試行を分けて設計する

通信が切れたとき、「決済されなかった」とは限りません。
リクエストは処理されたが、成功応答だけ受け取れなかった可能性があるためです。

| 成功条件 | 反例 | 確認内容 |
|---|---|---|
| 同キーの正常再要求は同じ結果を返す | 再要求ごとに新しい `chargeId` を作る | 初回と再要求の応答 |
| 内容が違う同キーを拒否する | 過去の成功を別の注文へ流用する | キーと本文の組合せ |
| 不正応答を成功扱いしない | 別の `orderId` の成功を採用する | 要求と成功応答の値 |
| 結果不明を保持する | 通信失敗を `paid` へ変える | 状態、再試行回数、受信した応答 |

### 入力プロンプト: 隔離検証と依存順の実装を進める

```text
まず隔離した scratch で、別プロセスの起動通知、port 0、
HTTP のタイムアウトと終了処理を検証してください。
時計・待機・通信の境界を注入し、同じキーの並行要求と容量の全方針を確認してください。
T2 として、契約と状態、並行性、入力の信頼境界、検査オラクルを独立レビューしてください。

各機能は、実装前の assertion Red を確認してから Green へ進めてください。
import/setup の失敗や skip は Red と呼ばないでください。
mutation は期待した理由で検出したものだけを数え、元のバイト列へ戻して再確認してください。
全体 gate と JavaScript 診断を実行し、結果を .experiment/result-baseline.json へ残してください。
```

今回のベースラインでは、4プロジェクトのテストと全体 gate、JavaScript 診断が成功しました。
一方、初期 Red のログには assertion の抜粋だけで、runner の全出力が残っていないものがあります。
後から保存した誤実装の再現結果は、実装前の完全な生ログがあったことの証明にはしていません。
失敗・中断・誤った fixture・不採用の再検査も履歴へ残しました。

## 実際の別プロセスを HTTP で接続する

### 入力プロンプト: 正常系と決済停止を動かす

```text
services/payments/main.mjs と services/orders/main.mjs を実際の別プロセスで起動してください。
loopback と port 0、IPC の起動完了通知を使って接続してください。
正常な注文、同キー要求、異なる内容の同キー、タイムアウトや不正応答を検査してください。

自分で起動して PID を追跡している payments だけを停止し、
orders の結果が payment_unconfirmed になることを確認してください。
結果不明の同じ注文を再要求しても、勝手に決済し直さない契約を確認してください。
固定 sleep や、停止できたか分からない kill を成功の根拠にしないでください。
```

今回の統合テストでは、標準サービス同士の接続と、拒否・遅延・リダイレクト・切断・不正応答などの専用 fixture を区別しました。
ダミーの拒否サーバーで検査した結果を、標準の payments が実際に拒否決済を行ったとは説明していません。

## `processedAt` 追加の影響先を調べる

次に、成功応答へ処理時刻を必須追加します。
提供側だけの修正で済ませず、検証器、利用側、固定 fixture、統合テストの影響も調べます。

### 入力プロンプト: 変更前に影響と期待結果を定める

```text
決済成功応答へ processedAt を必須追加したいです。
実装前に .sdd/specs/contract-change.md を作り、
contract、提供側、利用側、統合の影響を調べてください。

processedAt は YYYY-MM-DDTHH:mm:ss.sssZ の正規 UTC 表現とし、
文字列の形だけでなく実在する日時か確認してください。
欠落、不正な型、不正な暦日、非正規な表現は拒否してください。
同じ冪等キーを再要求したとき、初回と同じ processedAt を返してください。

正常な日時を受け付ける対照と、欠落や 2026-02-30 のような不正日付の反例を
仕様と独立した固定 fixture から作ってください。
まず契約側を更新し、提供側と利用側の実装は追従させずに検査してください。
どのプロジェクトが選ばれ、どの assertion が失敗したかを保存してください。
ロックや scope の拒否は、アプリの assertion Red と区別してください。
```

今回、契約側を更新した段階では、次のようになりました。

| 選ばれたプロジェクト | テスト結果 |
|---|---|
| `contract` | PASS |
| `services/payments` | FAIL |
| `services/orders` | FAIL |
| `integration` | FAIL |

提供側が時刻を返さず、利用側や統合側も新しい契約を満たしていないことを、実際の assertion で確認しました。
同時に発生した古いロック、古い証跡、未追跡ファイルの scope 拒否は、別の問題として保存しています。
gate が FAIL だったという事実だけを Red の証明にはしません。

## 両側を追従させて再承認・再検証する

### 入力プロンプト: 契約の変更を最後まで反映する

```text
確認した assertion Red から、提供側・利用側・統合を新契約へ追従させてください。
提供側は注入時計の正規 UTC 時刻を保存し、同キーの再要求で同じ値を返してください。
利用側は成功応答の required 項目と要求との一致を検査してください。
JSON の parse 成功や時刻らしい文字列だけで、成功とは判断しないでください。

共有 fixture やテストを変えたら、変えた理由と再検証の時点を記録してください。
変更した仕様を独立レビュー・再承認し、現在のファイルハッシュへ証跡を結びつけてください。
限定 mutation、元バイト列への復元、全体 gate、JavaScript 診断を確認してください。

最後に contract/schemas.json だけの一時的な差分で
npx musubix6 sdd gate --changed --json を実行し、
4プロジェクトが選ばれ、unknown や免除がないことを確認してください。
元のバイト列へ戻し、全体 gate も別に実行してください。
```

契約変更後は24要件・27テストとなり、全件成功しました。
現在のコード・テスト・オラクル・runner のハッシュへ結びついた18件の mutation を確認し、すべて復元しています。
途中の古い承認による拒否や、不完全な試行は検出成功へ数えていません。

最終の影響確認では、差分が `contract/schemas.json` の1ファイルだけであることを確認しました。
4プロジェクトの検査が選ばれ、scope の unknown は0、免除もありませんでした。
この changed gate は影響範囲の確認で、すべての証跡を再検査する full gate の代わりにはしていません。

## 2コンテナーを既存の opt-in で接続する

今回は、最初の設計で非 loopback bind と送信先 allowlist の opt-in を用意していました。
コンテナーへ移すために、安全側の既定値を後から無効化したわけではありません。

### 入力プロンプト: 公開範囲を限定して接続する

```text
wslc-containers を使い、公式 node:24-alpine で2つのサービスを実行してください。
専用のユーザー定義ネットワークへ接続し、payments という名前で DNS 解決してください。
コンテナー内の非 loopback bind は、既存の ALLOW_NON_LOOPBACK=true と HOST を明示してください。
orders の PAYMENT_URL と PAYMENT_ALLOWED_ORIGINS には、今回の payments の origin だけを指定してください。
bind と送信許可は別の条件として守り、既定の安全設定を弱めないでください。

ホストへ公開するのは orders の 127.0.0.1 のポートだけとし、
payments のポートはホストへ公開しないでください。
4プロジェクトの全テストを実コンテナーで実行してください。
```

今回、payments の名前解決を確認し、orders だけをホストの `127.0.0.1:51405` へ公開しました。
これは今回の割当値であり、読者は自分の環境の空きポートを使います。
payments のホスト公開はありません。

コンテナー内の検査は次のとおりで、全グループとも失敗・skip は0件でした。

| プロジェクト | 成功したテスト数 |
|---|---:|
| `contract` | 3 |
| `services/payments` | 8 |
| `services/orders` | 8 |
| `integration` | 11 |

## 決済コンテナーの停止・再起動で限界を確認する

### 入力プロンプト: 再起動後に保証が失われる範囲も試す

```text
ホストから正常な注文を作り、paid を確認してください。
決済へ同じキーを再要求し、chargeId と processedAt が同じことを確認してください。

自分の payments コンテナーだけを停止し、
新しい注文が payment_unconfirmed になることを確認してください。
payments を再起動しただけでは、その注文が自動的に paid にならないこと、
同じ注文を再要求しても勝手に再課金しないことを確認してください。
別の新しい注文は成功することも確認してください。

再起動前の決済キーを payments へ再要求し、メモリー内の冪等性が失われる限界も確認してください。
不利な結果を隠さず、再起動をまたぐ二重課金防止を保証しないでください。
自分のリソースだけを片づけ、ネイティブの全体 gate と JavaScript 診断を再実行してください。
```

今回の観測結果は次のとおりです。

| 状況 | 観測結果 |
|---|---|
| 通常の新規注文 | `paid` |
| 同じ決済キーの再要求、再起動前 | 同じ `chargeId` と `processedAt` |
| payments 停止中の新規注文 | `payment_unconfirmed` |
| payments 再起動後、同じ未確認注文を参照・再要求 | 未確認のまま。自動では確定しない |
| 再起動後の別の新規注文 | 成功 |
| 再起動前のキーを payments へ再要求 | 新しい `chargeId`。以前のキーを保持していない |

最後の結果は重要です。
プロセス内の冪等性テストが通っても、再起動をまたいだ二重課金防止にはなっていません。
この観測を、永続的な exactly-once の成功と説明してはいけません。

## つまずきと対処・未確認の範囲

| 症状 | 原因・確認点 | 対処 |
|---|---|---|
| 契約変更で提供側だけが検査される | 依存・成果物の利用関係が不足する | schema だけの差分で、4プロジェクトの選択を確認する |
| gate は落ちるが、テストが実行されていない | 古いロックや scope で停止している | 実際の assertion 失敗とは別に記録する |
| 時刻文字列があるのに不正な応答を採用する | 形だけを検査している | 必須項目、暦日、正規表現、要求との一致を検査する |
| payments の DNS 名へ接続できない | ネットワーク、bind、送信先許可のどれかが不足する | 3つを別々に確認し、許可を無制限に広げない |
| 再起動後に同じ決済キーが再実行される | 冪等情報がメモリーだけにある | 永続化と障害復旧を別要件にし、現状の保証を限定する |

外部決済事業者の正しさ、分散時計の整合性、クラッシュ耐久性、持続的な負荷性能は未確認です。
コンテナーの成功も、実データを扱う本番運用や公開の許可にはなりません。
この編で整えたのは、AI が変更の影響を判断する条件と、その判断を後から検査できる証跡です。
