# 第3編: 強制終了と復旧を検査するローカルジョブキューを開発する

Copilot CLI への日本語の依頼で、JSON に保存するジョブキューを作ります。
実ワーカーを6つの異なる故障点で強制終了し、再配布、古い取得権限の拒否、破損からの明示復旧を確認します。

対象は、[第1編](tutorial-app-development-1.md) の SDD/TDD と、プロセス・ファイル操作の基本を理解した読者です。
musubix6 0.2.0、Node.js 24.21.0 で2026年10月22日に再実装し、WSL コンテナーで検証した結果を反映しています。

## この編で作るものと完成条件

`job-queue` は、信頼するローカルディレクトリを複数の協調プロセスから使う学習用キューです。
ジョブ本体は JSON、排他制御だけは Node.js 組込みの SQLite を使います。

| 操作 | 役割 |
|---|---|
| `init` | 空の保存データを明示的に初期化する |
| `enqueue` | ジョブを追加する |
| `claim` | 処理できるジョブを取得し、取得トークンを返す |
| `ack` | 現在のトークンで完了を確定する |
| `fail` | 再試行可能なら ready、上限なら dead にする |
| `list` | 保存中の状態を読む |
| `recover` | ハッシュで指定した候補から明示的に復旧する |

保存ファイルが壊れた場合はエラーにし、空のキューへ置き換えません。
また、ジョブの外部副作用と `ack` は1つの原子的な操作ではありません。
同じジョブの副作用が繰り返されることを、実際の別プロセスで確認します。

入力プロンプトは、実際の指示を短縮・一般化した読者向けの例です。逐語録ではありません。
件数や成否は今回の実測値ですが、生成されるコードやテスト数の一致は保証しません。

## 前提条件と今回の実験環境

Linux、Git、Copilot CLI、Node.js 24 の ESM を使います。
アプリ実行時の外部 npm 依存はなく、SQLite は Node.js 組込みのものです。
musubix6 0.2.0 と ESLint 9.39.5 を開発用へ完全固定しました。
開発は GPT-6.1 Sol、独立レビューは Claude Sonnet 5.5 です。

検証は、1ホスト・同一 PID 名前空間・信頼するローカルファイルシステムに限定します。
ネットワークファイルシステム、別ホスト、悪意あるファイル差替えは対象外です。
コンテナー工程には WSL と `wslc.exe` が必要です。
初期化後に、同梱の `wslc-containers` スキルを Copilot から読み込めることも確認してください。
読み込めない場合は、スキルの配置とセッションの再起動を確認してから進めます。

今回の `approval: auto` は、ダミーデータによるローカル実験と AI の独立レビューを表します。
人間承認を受けたという記録ではありません。
強制終了するのは、自分で起動し PID を追跡している子プロセスだけです。
名前による一括 kill や、WSL 全体の停止は行いません。

## 保存・排他・状態・復旧を順に仕様化する

### 入力プロンプト: 機能の依存と検査条件を決める

```text
ローカル JSON ジョブキューを作ってください。
まず .sdd/plan.md と、次の機能の .sdd/specs/<feature>.md を作ってください。
atomic-store、file-lock、queue-core、visibility-timeout、recovery、cli、concurrency-test です。
依存する機能が検証済みになってから次へ進めてください。

各仕様に REQ/TEST ID、具体的な入力と期待結果、正常対照、境界・エラー、
REQ | PASS condition | counterexample | TEST/command | observed evidence の表を記載してください。
契約、信頼する入力、実行、判定、証跡履歴、統合・配布の6段階を確認してください。
有限の状態と方針は、許可・禁止を含めて表にしてください。

保存は世代番号と checksum を持つ JSON とし、一時ファイルと rename を使ってください。
読込み失敗は空配列へ置き換えず、バックアップや tmp を勝手に採用しないでください。
初期化は明示的に行い、現在の claimToken だけを ack/fail の権限にしてください。
外部副作用の exactly-once、物理的な電源断耐久性、全スケジュールの保証は対象外にしてください。
```

この題材は永続化と並行性を扱うため、実験では T2 として進めました。
設計上の期待だけでなく、実環境で成立するかを隔離した scratch で確かめます。

## ロックの前提を実測し、誤った開始を履歴へ残す

今回の最初の試行では、file-lock の実装が承認と本来の初回 Red より先に作られました。
この試行は BLOCKED として残し、後から成功した履歴へ読み替えていません。
却下した22ファイルをハッシュつきで保存し、誤った戻り値を返すスタブへ戻して進め直しました。

### 入力プロンプト: 排他制御の成立性を確認する

```text
排他制御の設計を、実装前に隔離した scratch で検証してください。
今回は、Node.js 組込み SQLite の排他的トランザクションをロックだけに使います。
キュー本体の JSON と、SQLite のロック用メタデータを分離してください。
同じ正規化済みパスと安定した inode を使い、生きている所有者を期限だけで追い出さないでください。
ロックの取得・競合・プロセス終了後の解放を実際の別プロセスで確認してください。

コールバック終了までの書込み、古い権限、失敗した close、
書込みとロック解放がともに失敗した場合の優先順位も仕様にしてください。
成立性検証と独立レビューの後に、assertion Red を確認してから本実装へ進んでください。
```

再開後は実装前の assertion Red を8件確認しましたが、途中でテストの期待方法にも誤りが見つかりました。
`assert.rejects` で入れ子の `cause` を単純なオブジェクトと比較しても、必要な Error の同一性を正しく検査できていませんでした。
predicate で同一性やプロパティを確認する形へ訂正し、実装後の再検証であることを明記しました。
エラーの cause を別物に置き換えてテストへ合わせたわけではありません。

このような「実装が先行した場合の履歴を保った再開手順」は、改善点として [#377](https://github.com/nahisaho/musubix6/issues/377) に登録しました。

## ジョブ状態と取得トークンを実装する

### 入力プロンプト: 状態と権限の反例を先に作る

```text
init、enqueue、claim、ack、fail、list を実装してください。
先に状態表とテストを作り、実装前の assertion Red を確認してください。
既定の maxAttempts は5とし、取得時の回数、失敗時の ready/dead、done の保持を定義してください。

claim は owner と新しい claimToken・claimGeneration を持つジョブを返してください。
ack/fail は現在のトークンを検査し、他の取得権限や古いトークンを拒否してください。
不正な入力、保存失敗、破損を成功へ置き換えないでください。
限定 mutation、元バイト列への復元、独立レビュー、全体 gate と JavaScript 診断まで行ってください。
```

今回の queue-core では12個の状態セルと試行回数の方針を確認しました。
同時プロセスによる追加・取得も有限のサンプルで検査しています。
30回の mutation 試行のうち、検出として認めたのは28件で、すべてを成功へ数えてはいません。
不採用の1件は、キュー側で書込みエラーを握り潰しても、下位の file-lock が失敗を伝搬したためテストが成功した試行です。
もう1件は assertion が失敗したものの、検査ハーネスが誤った失敗文言を期待していました。その変異は、修正したハーネスで別名の試行として検出を確認しました。

## 期限切れの取得を回収し、古い権限を失効させる

取得後にワーカーが死んだ場合、そのジョブを永久に処理中へ残すわけにはいきません。
一方、時刻が期限を過ぎただけで、現在の取得トークンを即座に無効にする設計でもありません。

### 入力プロンプト: 回収境界を定める

```text
visibility-timeout を追加してください。
回収の境界 D は (claimedAt + visibilityMs) + clockSkewMs とし、
now >= D でロック内の回収対象にしてください。
既定は visibilityMs=30000、clockSkewMs=1000 としてください。
境界の直前・同値・直後を注入時計で確認してください。

実際に回収される前なら現在トークンによる遅い ack/fail を認め、
回収・再取得後の古いトークンは ECLAIMLOST で拒否してください。
ジョブの期限と、生きたプロセスが持つロックの解放を混同しないでください。
```

この猶予は、分散した時計を同期する仕組みではありません。
今回の回収はロック内で行い、回収後の古い権限を拒否する条件を検査しました。

## 破損した保存ファイルを明示的に復旧する

復旧候補が読めるだけでは、後の更新を失わないとは限りません。
現在ファイルと候補ファイルを、それぞれ生バイト列の SHA256 で指定します。

### 入力プロンプト: 復旧の前提と情報損失を検査する

```text
recovery を追加してください。
現在ファイルと候補ファイルの raw-byte SHA256 を呼出し側に指定させ、
同じキューロック内で再読込みして照合してください。
JSON 内の論理 checksum を raw-file hash の代わりに使わないでください。

元の破損バイト列を固有の quarantine ファイルへ保存してから置き換えてください。
候補の schema/checksum、世代、パス、symlink や hardlink の拒否を検査してください。
正常な現在ファイルのロールバックや、ハッシュ不一致は拒否してください。
復旧した古い claimToken を失効させ、結果に LOSS_POSSIBLE と警告を含めてください。
完了済みの情報を失い、副作用が繰り返される可能性も実例で示してください。
```

今回の復旧では、ハッシュの方針144セルと、状態・試行回数24セルを確認しました。
実デモでは、完了したジョブが古い候補への復旧によって ready へ戻ることも確認しています。
`LOSS_POSSIBLE` は成功に付け足した飾りではなく、情報を失った可能性を示す結果です。
復旧後の list は別のロック取得で行う観測で、復旧と一体の原子的なスナップショットではありません。

## 1操作で終了する JSON CLI を用意する

### 入力プロンプト: CLI の入力と終了コードを固定する

```text
入口を bin/job-queue.mjs とする1操作だけの CLI を作ってください。
全操作で --dir を必須とし、payload は --payload の JSON で受け取ってください。
claim は --owner、ack/fail は --id と --token を使います。
recover は --candidate、--candidate-hash、--current-hash を必須にしてください。
ハッシュや取得権限を自動補完しないでください。

stdout は1行の JSON とし、成功は {ok:true,command,result}、
失敗は {ok:false,command,error:{code,message,...}} としてください。
成功・空の claim・help は終了0、構文エラーは2、業務エラーは3、未知や I/O の失敗は1です。
アプリ独自の説明文を stderr へ混ぜず、ランタイム由来の警告は隠さず別に保存してください。
stdin を待たず、操作後に終了してください。

不正引数で保存やロックの木を触らないことも確認してください。
構文の有限表、正常対照、エラー、独立レビュー、mutation と復元を検査してください。
```

今回の CLI 工程では377セルの入力文法を確認し、16件の mutation を検出して復元しました。
ネイティブ実行で SQLite の警告は観測されませんでしたが、出ない理由は未確認です。
警告を抑制した結果ではなく、他の環境でも出ないという保証にもしていません。

## 6つの異なる故障点で、実ワーカーを SIGKILL する

故障点へ到達する前に停止したプロセスは、その故障点を検証した証拠にはなりません。
IPC の通知と期限つきの待機で、停止位置と PID を確認します。

### 入力プロンプト: 強制終了の位置を区別して検査する

```text
concurrency-test を実装してください。
自分で起動・追跡した実ワーカーを、次の6つの異なる点で SIGKILL してください。
1. claim が呼出し元へ返った後、副作用の前。
2. 副作用を独立ファイルへ同期保存した後、ack の前。
3. 生きたロックを保持して更新する前。生存中の競合排除と死後の解放を確認。
4. 一時ファイルに正の一部分を書いた後、全量の write/fsync/rename が終わる前。
5. ack の保存・同期と API の復帰後。done が再配布されないことを確認。
6. claim の保存・同期後、取得結果を呼出し元へ返す前。

IPC/barrier、実 PID、生存確認、実際の SIGKILL 終了を assertion へ結びつけてください。
固定 sleep、空振りした kill、結果の固定値を証拠にしないでください。
1と6は返却済み件数で区別してください。
2では回収後の別ワーカーが同じ副作用を実行し得ることを示してください。
4では実際に書けた部分バイト列を読み、旧 current が完全で tmp が自動採用されないことを確認してください。
```

今回の6点はすべて、到達通知、kill 前の生存、実際の `SIGKILL` 終了を確認しました。
claim の返却後は取得結果が1件、返却前は0件で、同じ故障点を名前だけ変えた検査にはしていません。
部分書込みは全360バイト中180バイトを実測し、旧 current のハッシュが変わらないことを確認しました。
副作用後・ack 前の停止では、同じジョブの副作用が異なる PID で2回記録されました。

この工程では、CLI の検査 helper が過去の `demo.json` を上書きする問題も修正しました。
先に固定ファイルの不変性を検査する assertion Red を確認し、実行ごとに固有ディレクトリを割り当てています。
親セッションの再実行後も、追跡済みの過去の証跡は変わっていませんでした。
過去に上書きした事実は消していません。

## 20ジョブの正常対照と、実 CLI の復旧を確認する

### 入力プロンプト: 集合と失敗理由を独立に比較する

```text
正常対照では payload 0..19 の20ジョブを登録し、
4つの実ワーカー全員が準備できてから同時に開始させてください。
登録 ID と payload、IPC の実行記録、独立したディスク記録、最終 done の集合を比較してください。
全ワーカーが実際に処理し、重複と欠落がないことを確認してください。

さらに実 CLI を別プロセスで起動し、3ジョブの追加、claim、ack、
current の破損、list の ECORRUPT、明示 recover、
古い token の ack に対する ECLAIMLOST を確認してください。
成功と、期待した業務エラーの終了3を区別してください。
quarantine が元の破損バイト列と同一で、候補が変わらないことも確認してください。

限定 mutation と復元、全体 gate、JavaScript 診断を実行してください。
SDD の red コマンドの終了0と、その中のテストの終了1を区別して記録してください。
```

今回の正常対照は、4ワーカーすべての実処理を確認しました。
期待値は実装の出力ではなく、固定した `0..19` です。
登録、IPC、ディスク、最終状態で ID と payload の対応が一致し、欠落・ID 重複は0件でした。
これは故障を伴うすべての実行で exactly-once を保証したという意味ではありません。

CLI デモは9つの実プロセスで行い、`ECORRUPT` と `ECLAIMLOST` は終了3でした。
復旧は `LOSS_POSSIBLE` を返し、破損バイト列の保存と候補の不変性も確認しました。
この工程の限定 mutation は12件です。
そのうち2件は SDD の Red コマンドで実行しており、外側の終了0を「変異が生き残った」とは判断していません。
内部テストの終了1、assertion の失敗理由、復元後の Green を確認しています。

ネイティブ工程の最終状態は55要件・57テストで、親セッションの全体 gate と JavaScript 診断も PASS でした。
ただし、初回 Red の後に CODE の所有関係が変わって拒否された回や、実装後の修復・強化も履歴に含まれます。
既存 CLI の8件は helper 変更に伴う setup-only の refactor 記録で、新しい Red を確認したとは説明していません。
gate の57/57という表示だけから、全件が最初の実装前 Red から一直線に進んだと判断してはいけません。

## 同じ PID 名前空間の WSL コンテナーで確認する

### 入力プロンプト: 故障点を削らず全試験を動かす

```text
wslc-containers を使い、公式 node:24-alpine でキューを検査してください。
強制終了と回収を含むアプリ全テストを実際に実行し、
件数、失敗、skip、終了コードを保存してください。
PID 1や子プロセスの回収の違いで失敗したら、その失敗を残して起動方法を修正し、
故障点を削らず同じ全試験を再実行してください。

新しい専用の名前付きボリュームへ20ジョブを登録し、
1つのコンテナー内で4つの実ワーカープロセスを同時起動してください。
ワーカーを別々のコンテナーへ分けないでください。
登録 ID、実行と確定の記録、最終状態を独立に比較し、重複と欠落を数えてください。
自分の資源だけを片づけ、ネイティブの全体 gate と JavaScript 診断も再実行してください。
```

公式 `node:24-alpine` の検証用イメージで、全59テストが成功しました。
失敗・skip・cancelled は0件で、コンテナーの inspect でも終了0を確認しました。
6つの故障点で到達通知、生存、実際の SIGKILL を確認し、同じジョブの副作用が2回生じる結果も再現しました。
部分書込みはコンテナー内では全356バイト中178バイトでした。PID などを含むため、ネイティブでの360バイト中180バイトとは長さが異なります。
今回、PID 1の回収失敗は観測しておらず、別の init への差替えは行っていません。

ただし、名前付きボリュームの実演は、最初の非対話実行ではマウントするコマンドの許可を得られず停止しました。
この時点の結果は BLOCKED のまま保存し、コンテナーの一時領域で成功した20ジョブの正常対照を代わりにはしていません。
対話セッションで人間が実行を承認した後、同じソースから実行用イメージを再作成し、新しい専用ボリュームで実演しました。
ここで受けたのは、この追加実行の許可です。先の `approval: auto` を人間による仕様承認へ読み替えたわけではありません。

| 名前付きボリュームの実測 | 結果 |
|---|---|
| 外部通信・公開ポート | `--network none`、公開なし |
| 実プロセス | Node.js が PID 1、同一コンテナー内の4ワーカー |
| 開始時の対照 | 全ワーカーが1件ずつ取得して待機し、4件 claimed・16件 ready |
| 登録・取得・完了確定・最終 done | それぞれ20件 |
| 期待値 | 実装の出力ではなく payload `0..19` |
| 重複確定・欠落 | いずれも0件 |
| 独立照合 | 登録、PID 別のディスク記録、別 CLI の list、保存 JSON が一致 |

親セッションでも生の記録を読み直し、4ワーカー全員の処理、実際の volume mount、終了0を確認しました。
自分で作成したコンテナー、専用ボリューム、実行用イメージを削除し、共有の公式ベースイメージは残しました。
証跡の取り出しでは、最初の `wslc cp` がディレクトリ宛先の末尾区切り不足で失敗し、区切りを付けた再実行で保存できました。
この失敗は取得処理のもので、アプリの検査失敗へも成功へも読み替えていません。

コンテナー用には、照合器と実演ランナーを対象とする2要件・2テストを追加し、10件の限定 mutation を検出・復元しました。
途中の TypeError による Red は不採用とし、修正前に assertion Red を確認し直した履歴も残しています。
また、一時ビルド領域の削除後に strict scope が不一致となった gate は失敗として残しました。
テスト本体や方針は変えず、2テストの setup-only refactor 記録を更新して再検証しています。
最終状態は57要件・59テストで、親セッションの全体 gate と JavaScript 診断も PASS でした。
ただし、失敗証跡そのものの書込みに失敗する AggregateError 分岐は、故障注入していません。

## つまずきと対処・未確認の範囲

| 症状 | 原因・確認点 | 対処 |
|---|---|---|
| gate の Red が記録できない | import、setup、CODE の所有関係、実装先行などを区別する | 不採用の履歴を残し、実際の assertion と正規の再検証手順を確認する |
| kill したのに故障点を検証できていない | 到達前に終了、別 PID、signal が未確認 | IPC の位置、生存、終了 signal を assertion で確認する |
| 古いワーカーが完了できない | 回収後のトークンが失効した | ECLAIMLOST を処理し、古い権限を復活させない |
| 復旧後に完了済みジョブが再び ready になる | 古いスナップショットへ戻した | LOSS_POSSIBLE を確認し、外部副作用の重複を別途扱う |
| 再検証で過去の証跡が変わる | 固定した出力パスを再利用している | assertion Red から修正し、実行ごとの固有パスと変更前後の比較を使う |
| 名前付きボリュームの実演が起動しない | 非対話セッションで実行許可を取得できない | 未実施として停止し、対話的な許可後に同じ条件で実行する。権限設定を迂回しない |

SIGKILL は物理的な電源断ではなく、ディスクやコントローラーが fsync を正しく実行した証明にもなりません。
全スケジュール、公平性、持続的な処理性能、NFS、別 PID 名前空間の共有は今回の保証範囲外です。
復旧と再配布が動いても、外部副作用の exactly-once は保証しません。
