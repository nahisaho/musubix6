# チュートリアル 3: 永続化と並行性のあるアプリを、慎重に開発する(ファイル保存のジョブキュー)

[チュートリアル 2](tutorial-app-development-2.md) では、5 機能の HTTP API を、機能ごとに慎重に開発しました。このチュートリアルでは、さらに難易度を上げます。題材は、データをファイルに保存し、複数のプロセスから同時に使われるジョブキューです。

| | チュートリアル 2 | このチュートリアル |
|---|---|---|
| 題材 | 在庫つきの注文受付 HTTP API | ファイル保存のジョブキュー(ライブラリと CLI) |
| 規模 | 5 機能(REQ 46 件) | **7 機能**(REQ 102 件、テスト 133 件) |
| 区分 | T2 | T2(全機能) |
| 主なリスク | 認証、状態遷移、在庫の整合性 | **途中で止まるプロセス、複数プロセスの競合、壊れたファイル** |
| 新しく使うもの | 機能の分割、`## Design`、並列レビュー、再承認 | **実現性のスパイク**(承認の前に危うい前提を実験する)、**複数プロセスのテスト**、強制終了(SIGKILL)の注入、長い作業の分け方、不安定なテストの調査 |

ここに載せたプロンプトと結果は、`/tmp/musubix6-tutorial-3/job-queue` で実際に開発したときの記録です(Node.js 24、Copilot CLI)。最後の「再実験での確認結果」に、同じプロンプトを最初からやり直した結果を載せています。

## 進め方の約束

- チュートリアル 1、2 と同じです。読者は、**プロンプトを入力すること**だけを行います。
- **プロンプトにスキル名は不要です。** 内容に合わせて、エージェントが必要なスキルを選びます。
- 「エージェントが実行すること」は、内部の作業の記録です。読者は実行しません。

- 1 つのプロンプトの実行は、約 10 分で打ち切りました(検証の都合です)。長い作業は、プロンプトを分けます(§6 を参照)。

## 2. 機能に分割して、最初の spec を作る

ジョブキューは、永続化、排他、状態遷移、復旧、並行テストが絡み合います。最初に機能へ分割して、作る順序を決めます。

### 入力プロンプト

```text
ファイルに保存するジョブキューのライブラリと CLI を作りたい。ジョブはディスクに永続化し、書き込みは途中で止まっても壊れないようにする(一時ファイルに書いて rename)。複数のプロセスから同時に使っても安全にしたい(ロックファイル)。ワーカーは、ジョブを取得(claim)し、成功(ack)か失敗(fail)を返す。取得したまま応答がなければ、一定時間(可視性タイムアウト)で他のワーカーが取得できるようにする。クラッシュで壊れたファイルからも復旧したい。複数のワーカープロセスを同時に動かしても、同じジョブが二重に処理されないことをテストで示したい。
機能が多いので、機能に分割して、作る順序と依存関係を決めて。そのあと、最初の機能の要件定義書を作って。
```

エージェントは、次の `.sdd/plan.md` を作りました。

```md
| order | feature | depends | note |
| --- | --- | --- | --- |
| 1 | atomic-store | - | JSON の読み書き。一時ファイル→fsync→rename で書き込み中断に耐える |
| 2 | file-lock | - | ロックファイルによる排他(O_EXCL)。古いロックの回収 |
| 3 | queue-core | atomic-store, file-lock | enqueue / claim / ack / fail。ロック下で read-modify-write |
| 4 | visibility-timeout | queue-core | claim の期限切れで他ワーカーが再取得できる。試行回数 |
| 5 | recovery | atomic-store, queue-core | 壊れたファイルの検出と、.bak / 残骸 tmp からの復旧 |
| 6 | cli | queue-core, visibility-timeout, recovery | enqueue / claim / ack / fail / list / recover コマンド |
| 7 | concurrency-test | queue-core, visibility-timeout, cli | 複数ワーカープロセスで二重処理ゼロを実証 |
```

最初の機能 `atomic-store` は、T2 の spec(REQ 8 件)になりました。`## Design` には、tmp ファイルの命名、手順(シリアライズ → open → write → fsync → rename)、退けた案(直接上書き)が書かれています。

## 3. 承認の前に、最も危うい前提を実験する(スパイク)

この題材の設計は、2 つの前提の上に立っています。

1. 同じディレクトリでの `rename` は、読み手に「旧内容か新内容のどちらか」しか見せない。
2. 複数のプロセスが同時に排他作成(`O_EXCL`)すると、勝者がちょうど 1 つになる。

前提が外れると、spec を承認して実装を進めたあとで、設計をやり直すことになります。そこで、**承認の前に**、小さな実験(スパイク)で確かめます。

### 入力プロンプト

```text
.sdd/specs/atomic-store.md を承認する前に、この題材で最も危うい前提を、小さな実験(スパイク)で確かめたい。
具体的には、(1) 同じディレクトリの rename が、書き込み中の読み手に「旧内容か新内容のどちらか」しか見せないこと、(2) 複数プロセスが同時に排他作成(O_EXCL)したとき、勝者がちょうど 1 つになること、の 2 点。
実際に複数プロセスを動かして試して。スパイクのコードは本実装と分けて spikes/ に置き、結果と、設計に与える影響を spec の Design に反映して。
```

エージェントは、`spikes/rename-visibility.mjs`(書き手 1 つと読み手 4 つ)と `spikes/excl-create.mjs`(16 プロセス × 200 ラウンド)を作って、実際に動かしました。結果は次のとおりです。

| 前提 | 結果 |
|---|---|
| rename の可視性 | 2463 回の読み取りで、旧内容と新内容以外は **0 件** |
| 対照: 直接上書き | 41837 回のうち **40354 回**で、途切れた内容を読んだ |
| `O_EXCL` の排他 | 全ラウンドで勝者がちょうど 1 つ。敗者のエラーはすべて `EEXIST` |

対照実験があるため、「直接上書きを退けた」という設計判断が、推測ではなく実測で裏付けられます。設計への影響は、tmp ファイルを `wx`(排他作成)で開くことだけでした。

> **ポイント**
> スパイクの記録には、未検証の範囲も書かれます。このときは「試したのは 1 種類のファイルシステムだけで、ext4、xfs、NFS は未実施」「電源断への耐久性は未検証」でした。この記述は、次の節のレビューで、さらに厳しく見直されました。

## 4. 観点別の並列レビューと承認(T2)

### 入力プロンプト

```text
.sdd/specs/atomic-store.md は永続化の土台で、データを失うリスクがあるので、慎重にレビューしたい。
データ整合性、正しさ、公開インターフェース、テストの十分さの観点ごとに、別々のエージェントで並列にレビューして。指摘は spec に反映して、承認まで済ませて。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。
```

チュートリアル 2 の教訓に従い、レビューの記録は、機能ごとの別ファイル(`.sdd/review-atomic-store.md`)に保存させます。4 観点から約 25 件の指摘が出て、すべて spec に反映されました。主なものは次のとおりです。

| 観点 | 重大度 | 指摘 | 対応 |
|---|---|---|---|
| データ整合性 | High | fsync と close の順序、rename の後に失敗したときの結果が未定義 | 順序を要件に明記する。結果を `EDURABILITY` として定義する |
| データ整合性 | High | `write` が一部しか書かない場合(短い書き込み) | 全量を書くまでループする。進まなければ失敗にする |
| 正しさ | High | 「保存して deep-equal」と「`undefined` だけ拒否」が両立しない(`NaN` は `null` になる) | 受け付ける値を再帰的に定義し、それ以外は書く前に `TypeError` にする |
| 正しさ | Medium | 空ファイルや `EACCES` を、`undefined` や `ECORRUPT` に誤分類する | `ENOENT` のときだけ `undefined` にする。ほかは再送出する |
| スパイクの記述 | Medium | 「tmpfs で確認した」と書いたが、実装は `os.tmpdir()` を使うだけで、実行時に確認していない。tmp 名と `wx` の再試行も、スパイクでは試していない | スパイクの結果を、実測できた範囲(可視性と排他性)に限定して書き直す |

最後の指摘は、**実験の結果を過大に書いていた**ことへのものです。スパイクを書いたのと別のエージェントがレビューするため、こうした指摘が出ます。

> **確認の観点**
> 承認の記録は、`review-atomic-store.md` の先頭の `verdict: pass` と `open: 0` です。T2 の spec は、承認の時点でハッシュによってロックされます。

### 入力プロンプト

```text
.sdd/specs/atomic-store.md の全要件を実装して。
先に全テストを書いて Red を確認し、実装して Green にして。最後に全体の gate を通して、コミットして。
```

```text
SDD GATE PASS
✓ lock atomic-store: ok [ai, review file]
✓ trace: 12 REQ, 0 errors, 1 warnings
✓ ledger: 24 entries, chain intact
✓ tdd evidence: 12/12 tests Red→Green
✓ cmd test (0.5s)
```

書き込みの途中停止は、テスト用の子プロセスで再現します。子プロセスは rename の直前で止まり、親が SIGKILL を送ります。そのあと、元のファイルが無傷であることを確認します(`TEST-STORE-003`)。

実装中に、エージェントは spec との 2 つのずれを、自分で報告しました。

- テストで乱数を固定するため、`createAtomicStore` に任意のオプション `random` を足した。
- 不正な UTF-8 のときの `cause` は、spec の `SyntaxError` ではなく `TypeError` だった。

## 6. 次の機能へ(file-lock → queue-core → visibility-timeout → recovery → cli → concurrency-test)

2 機能目以降は、「次の機能に進んで」と依頼します。ただし、この題材では、**spec、レビュー、実装を 1 つのプロンプトで通すと、約 10 分では終わりません**。実際、最初に 1 つのプロンプトで頼んだ file-lock は、時間切れになりました。そこで、機能ごとに次の 2 つのプロンプトに分けます。

1. spec を作り、レビューして承認する(「実装はまだしないで、承認までで止めて」)
2. 実装して gate を通し、コミットする

機能の名前と数は、実行のたびに変わります。2 つ目のプロンプトに書く spec のファイル名(`.sdd/specs/<機能名>.md`)は、`.sdd/plan.md` の名前に読み替えてください。

### 6.1 file-lock(古いロックの回収)

この機能の最も危うい前提は、「古いロックを回収するとき、2 つのプロセスが同時に『自分が回収した』と思い込まない」ことです。プロンプトにそのリスクを書き、スパイクも依頼します。

```text
.sdd/plan.md の次の機能に進んで。古いロックの回収で、2 つのプロセスが同時に「自分が回収した」と思い込まないことが重要なので、慎重に進めたい。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、最も危うい前提は先に小さなスパイクで確かめて、結果を Design に反映して。そのあと、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。実装はまだしないで、承認までで止めて。
```

スパイクでは、16 プロセス × 300 ラウンドで、古いロックを一斉に回収させました。

| 方式 | 複数のプロセスが「回収した」と判定したラウンド |
|---|---|
| 対照: 観測して、unlink して、`wx` で作る | **171 / 300** |
| 世代ファイル(`<lock>.<N>`)を `link()` で作る(比較して置き換える方式) | **0 / 300** |

最初のスパイクのコードには、「観測した世代が古いかを確認せずに、最新の世代を作る」誤りがあり、268 / 300 で複数の回収者が出ました。エージェントは、これを設計の欠陥ではなくスパイクの誤りと判断して、直しました。この失敗から、「回収は、観測した世代が古いときだけ」という条件が必須だとわかり、要件に入りました。

並列レビュー(4 観点)では、設計に関わる指摘が 2 件出ました。

> **COR-1: 世代番号の再利用(ABA)**
> 古い世代を掃除すると、長く止まっていた観測者が、削除済みの `N+1` を `link()` で再作成できる。より新しい世代があるのに、回収に成功したと誤認する。
>
> **COR-2: lease を超えた保持者との重複**
> lease(貸出期間)が切れても、保持者が生きて処理を続けていれば、回収者と重なる。「重ならない」という保証は、成立しない。

COR-1 には、「link のあとで世代を再列挙し、より新しい世代があれば、自分の世代だけを削除して負けを認める」という要件(`REQ-LOCK-015`)を追加しました。COR-2 には、保証の範囲を「lease の内に終えるか、死ぬ保持者」に**狭めて**、spec に明記しました。世代番号を fencing 番号(古い保持者の書き込みを拒否するための番号)として公開し、検証は queue-core に引き継ぎます。

実装を依頼します。

```text
.sdd/specs/file-lock.md の全要件を実装して。
先に全テストを書いて Red を確認し、実装して Green にして。最後に全体の gate を通して、コミットして。時間がかかる処理が多いので、途中で止まらないように、テストは小さい時間単位で書いて。
```

#### つまずいた点: 1 つのプロンプトでは時間切れになった

最初の記録では、spec から実装までを 1 つのプロンプトで頼みました。4 観点のレビューが終わり、テストを書く途中で、10 分の制限に達しました。このとき、`gate` は次のように失敗していました。

```text
SDD GATE FAIL
✓ lock file-lock: ok [ai, review file]
✗ tdd evidence: 12/27 tests Red→Green
    TEST-LOCK-001 (REQ-LOCK-001): no Green recorded
```

承認は済んでいて、テストが一部ありました。リポジトリの状態にすべてが残っているため、新しい依頼で、続きから進められます。

```text
直前の作業が途中で止まった。.sdd/plan.md と git の状態から、途中だった機能を特定して、続きから進めて。テストが失敗していれば、原因を調べて直して。先に残りのテストを書いて Red を確認し、実装して Green にして。最後に全体の gate を通して、コミットして。重い確認は小さく分けて実行して。
```

実際の記録では、機能名を書いて依頼しました。結果は、27/27 が Red → Green の PASS でした。

```text
✓ tdd evidence: 27/27 tests Red→Green, 8 weak Red — Red came from setup/load, not the asserted behaviour …
```

weak Red とは、Red の原因が、検証したい挙動ではなく、テストの準備(未実装のスタブ)にあった記録です。gate は警告として残します。

### 6.2 queue-core(二重処理とロック保持中の死)

```text
.sdd/plan.md の次の機能に進んで。ジョブの二重処理が起きないことと、ロックを持ったままプロセスが死んでもジョブが消えないことが重要なので、慎重に進めたい。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。実装はまだしないで、承認までで止めて。
```

レビューの結果、次の設計になりました。

- ジョブは削除しません。状態を、1 回の atomic write でまとめて更新します。ack のあとも `done` として残ります。
- `ack` と `fail` は、`claimToken` の一致を要求します。
- ロックの世代番号(fence)を検証して、ロックを奪われた古い保持者の書き込みを拒否します。
- 「二重処理しない」という保証には、条件をつけます。対象は、lease の内に処理を終える保持者と、死ぬ保持者だけです。理由は §6.1 の COR-2 と同じです。

```text
.sdd/specs/queue-core.md の全要件を実装して。
先に全テストを書いて Red を確認し、実装して Green にして。最後に全体の gate を通して、コミットして。時間がかかる処理が多いので、途中で止まらないように、テストは小さい時間単位で書いて。
```

#### つまずいた点: 8 プロセスで、ロックの取得がタイムアウトした

記録では、このプロンプトに「小さい時間単位で」の依頼がなく、再び時間切れになりました。`TEST-QUEUE-008`(8 つのワーカーが同時に処理するテスト)も、`timed out acquiring …/queue.lock` で失敗していました。続きの依頼で、エージェントは原因を特定しました。

> 実装のバグではなく、テスト用のワーカーが、ロックの待ち時間(`lockTimeoutMs`)を既定の 10 秒のまま使っていたため。8 プロセスが同じロックを取り合うと、テスト全体で 15〜18 秒かかり、待たされたワーカーが落ちる。

ワーカー側で待ち時間を延ばして直し、全 40 テストが Red → Green になりました。**複数プロセスのテストは、待ち時間を明示しないと、負荷によって結果が変わります。**

### 6.3 visibility-timeout(時間の扱い)

```text
.sdd/plan.md の次の機能に進んで。時間の扱い(時計のずれ、期限ちょうど、遅れて戻ってきた古いワーカーの ack)が重要なので、慎重に進めたい。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。実装はまだしないで、承認までで止めて。
```

5 観点(時間、遅れた ack、クラッシュ、公開インターフェース、テスト)で、再レビューを 3 回繰り返しました。主な決定は次のとおりです。

- 期限は、`visibilityMs`(30 秒)に、時計のずれの許容(1 秒)を加えた幅です。**期限ちょうど**で期限切れになり、その 1 ミリ秒前までは有効です。
- 遅れて戻ってきた古いワーカーの `ack` は、時刻ではなく**状態**で判定します。誰にも再取得されていなければ、期限後でも成功します。再取得や回収のあとなら、`ECLAIMLOST` で拒否します。
- 試行回数が上限(5 回)に達したジョブは、再配布しません。

再レビューを重ねる中で、`TIME-001`(期限の判定条件の矛盾)や、`TEST-003`(境界値のテストが仕様と逆)のような、**spec の内部の矛盾**が見つかりました。実装の前に見つけられたのは、並列レビューの成果です。

### 6.6 concurrency-test(最終的な証明)

最後の機能は、「複数のワーカープロセスを動かして、途中で強制終了しても、二重処理ゼロ、取りこぼしゼロ」を示すテストです。テストが**たまたま通る**ことを防ぐのが、最も重要です。

```text
.sdd/plan.md の次の機能に進んで。これが全体の最終的な証明になる。複数のワーカープロセスを実際に同時に動かし、途中で一部のワーカーを強制終了(SIGKILL)しても、全ジョブがちょうど 1 回処理される(二重処理ゼロ、取りこぼしゼロ)ことを示すテストにしたい。テストが不安定(たまたま通る)にならないことが重要なので、慎重に進めたい。要件定義書を作り(ヒアリングは「おまかせ」で推奨値)、リスクの観点ごとに別々のエージェントで並列にレビューして指摘を反映し、承認して。レビュー結果は機能ごとに別のファイル(.sdd/review-<機能名>.md)に記録して、既存のものを上書きしないで。実装はまだしないで、承認までで止めて。
```

6 観点で、3 ラウンドのレビューを経て、次の設計になりました。

- 強制終了は、「待機点でプロセスを止めてから SIGKILL」にします。次の 6 種類の局面を、必ず 1 回ずつ通します。claim の直後、副作用の後、ロック保持中、書き込みの途中、ack のコミットの後、claim のコミットの後です。空振りしたら、テストを失敗にします。
- **検出力の証明**として、わざと壊した実装(ロックなし、トークンを無視する実装)が、テストで確実に検出されることを、要件にします。
- 「ちょうど 1 回」の定義は、次のとおり「おまかせ」で選ばれました。ジョブの二重保持と取りこぼしは、強制終了があっても厳密にゼロです。副作用の重複は、ack の前に強制終了された保持者によるものだけ許容します。副作用と ack を原子的にできないためです。厳密にしたければ、冪等キーが必要で、別の機能になります。

```text

先に全テストを書いて Red を確認し、実装して Green にして。最後に全体の gate を通して、コミットして。時間がかかる処理が多いので、途中で止まらないように、テストは小さい時間単位で書いて。
```

## 7. 本当に動かして、壊して、復旧する

テストが通ったことと、人間が CLI を使えることは、別の確認です。実際に動かして、ファイルを壊し、復旧する様子を見ます。

### 入力プロンプト

```text
job-queue の CLI を、実際に動かして確かめたい。作業用のキューを作ってジョブを 3 件登録し、1 件を claim して ack する。次に queue.json を途中で切れた状態に壊して、CLI がどう警告して止まるかを見せて。そのあと復旧して、残りのジョブが失われていないことを示して。最後に、確認していないことがあれば教えて。作業用のファイルは、後片付けして。
```

エージェントは、一時ディレクトリで、次の順に確かめました。

| 操作 | 結果 |
|---|---|
| `init`、`enqueue` を 3 回 | ジョブ a、b、c が `ready` |
| `claim`、`ack`(a) | a が `done`、b と c が `ready` |
| `queue.json` を先頭の 60 バイトだけにする | `list`、`enqueue`、`claim` が、どれも `ECORRUPT` で**終了コード 5**。何も書かない。`details` に、有効な復旧の候補として `queue.json.bak` が出る |
| `recover --source queue.json.bak --sha256 … --queue-sha256 …` | 復旧する。警告は `LOSS_POSSIBLE`。壊れたファイルは `queue.json.corrupt-…` に退避される |
| 復旧後の `list` | b と c は `ready` のまま |

そして、**重要な発見**がありました。`.bak` は 1 回前の書き込みの状態であるため、復旧すると、a の `ack` が失われ、`done` ではなく `claimed` に戻りました。b と c は失われていません。a は、30 秒の可視性タイムアウトのあとに再配布されうるため、重複処理に注意が必要です。

> **ポイント**
> `LOSS_POSSIBLE` の警告は、まさにこの状況のためにあります。「復旧すれば、最後の更新が失われうる」ことを、spec が最初から認めていて、CLI は黙って復旧しません。人間が `--sha256` で復旧元を指定する設計だったため、安全に確認できました。

エージェントは、確認していないことも報告しました(並行実行とロック競合、`fail` と試行上限、`--payload-file`、`.bak` も壊れている場合など)。これらの多くは、すでにテストが対象にしています。

## 9. たまに失敗するテストを調べる

ここまでの作業で、**同じ gate が、1 回目は失敗して、再実行すると通る**場面が 3 回ありました。落ちたテストは、`TEST-QUEUE-008` や `TEST-STORE-003` のように、毎回違いました。複数プロセスのテストでは、これを放置できません。原因の調査を依頼します。

### 入力プロンプト

```text
全体の gate や npm test が、たまに失敗する(実行のたびに違うテストが落ちる)。原因を調べて直したい。
npm test は 1 回に 30 秒ほどかかるので、時間切れにならないよう、まず 4 回だけ繰り返して失敗の頻度と落ちたテストを調べて。落ちたテストは、単独で何度も繰り返して再現させて原因を特定して。実装のバグなら実装を、待ち時間や負荷への弱さならテスト側を直して。直したら、同じ回数を繰り返して比べ、全体の gate を通して、コミットして。
```

記録では、次のとおりでした。

- 素の状態の `npm test` は、4 回とも成功し、再現しませんでした。そこで、落ちたテストを単独で、並列に負荷をかけて繰り返しました。
- `TEST-STORE-003` は、負荷の下で **120 回中 6 回**失敗しました。「SIGKILL を期待したのに `null` だった」という失敗です。
- 原因は、テスト用の子プロセス `support/hold-before-rename.mjs` でした。保留した Promise だけではイベントループが維持されず、親が SIGKILL を送る前に、子が自分で終了することがありました。**実装のバグではなく、テストを支える部品の問題**でした。
- 子プロセスに、終了を防ぐタイマー(`setInterval`)を足して直しました。同じ負荷での 120 回は、**0 件の失敗**でした。
- `TEST-QUEUE-008` は、12 回の負荷試験でも再現せず、原因は特定できませんでした。エージェントは、「原因は特定できていない」と明記しました。

> **ポイント**
> 「直した」と「直ったと確認した」は別です。前後で同じ回数を繰り返して、失敗の頻度を比べる依頼にしたため、効果が数字で示されました。特定できなかった原因を、正直に報告させることも大切です。
