# 第2編: 在庫と状態遷移を持つ注文 API を開発する

Copilot CLI への日本語の依頼で、認証・在庫・注文を扱う HTTP API を作ります。
在庫の引当途中で失敗した場合と、キャンセルを繰り返した場合も検査し、実際の HTTP 操作まで確認します。

対象は、[第1編](tutorial-app-development-1.md) の仕様・反例・Red/Green の区別を理解した読者です。
musubix6 0.2.0、Node.js 24.21.0 で2026年10月22日に再実装した結果を反映しています。

## この編で作るものと完成条件

`order-api` は、単一プロセスのメモリー上に商品と注文を持つ学習用 API です。
注文の支払操作はダミーの状態変更で、実際の決済ではありません。

| 確認対象 | 完成条件の例 |
|---|---|
| 認証 | ヘルスチェック以外はダミー API キーで保護する |
| 引当 | 在庫10の商品を3個注文すると在庫7になる |
| 状態遷移 | 作成、支払済み、発送済み、キャンセルの許可・禁止を区別する |
| キャンセル | 2個の注文をキャンセルしたら、2個だけ在庫へ戻す |
| 二重操作 | 同じキャンセルの再実行で在庫を二重に戻さない |
| 再起動 | データが消えることを確認し、永続化済みとは説明しない |

入力プロンプトは、今回の実際の指示を読者向けに短縮・一般化した例です。逐語録ではありません。
掲載する件数と結果は実測値ですが、読者の生成物が同じ構成や件数になることまでは保証しません。

## 前提条件と今回の実験環境

第1編と同じ Linux、Git、Copilot CLI、Node.js 24 の環境を使います。
musubix6 0.2.0 と ESLint 9.39.5 は開発用依存へ完全固定し、アプリの実行時依存にはしません。
開発は GPT-6.1 Sol、独立レビューは Claude Sonnet 5.5 を使いました。

コンテナー工程だけは、WSL と `wslc.exe` が必要です。今回は3.0.4.0を使いました。
他のプロジェクトと共有する環境のため、既存のコンテナーやイメージを一括削除してはいけません。

今回もダミーデータのローカル実験で、`approval: auto` を使っています。
人間の回答・承認を受けたという意味ではありません。実際の秘密情報、決済、公開は対象外です。

### 入力プロンプト: API 用の環境を初期化する

```text
このディレクトリを order-api 用の新しい Git リポジトリにしてください。
Node.js 24、ESM、アプリ実行時の外部 npm 依存なしで作ります。
```

準備後は同じディレクトリでセッションを開き直し、導入したスキルを使います。

## 認証・在庫・注文を機能へ分ける

一度に全機能を書き始めると、在庫や認証の前提が後から変わりやすくなります。
まず機能の依存と、状態変更の契約を固定します。

### 入力プロンプト: 実装前に仕様と依存を決める

```text
商品在庫と注文を扱う学習用 HTTP API を作ってください。
まず .sdd/plan.md と機能ごとの .sdd/specs/<feature>.md を作ってください。
auth、inventory、order-create、order-fulfillment、order-cancel に分け、
依存する機能が検証済みになってから次へ進めてください。

ヘルスチェック以外は X-API-Key で認証してください。
キーは起動時の API_KEYS という JSON 配列で渡す公開ダミー値だけを使います。
欠落・誤り・重複ヘッダーの扱いを決め、認証失敗で状態を変えないでください。

商品と在庫、注文はメモリーに持ち、再起動では消える設計にしてください。
注文作成は全商品の在庫を引き当て、途中失敗では全体を元に戻してください。
状態は created、paid、shipped、cancelled とし、
pay・ship・cancel の許可と禁止を全状態について表にしてください。
cancel で在庫を一度だけ戻し、shipped と cancelled からの cancel は拒否してください。

REQ と TEST ID、PASS 条件と具体的な反例、正常対照・境界・エラーを記載してください。
契約、信頼する入力、実行、判定、証跡履歴、統合・配布の6段階も確認してください。
単一プロセスで扱うこと、実際の決済や永続化はないことを明記してください。
```

今回の機能分割は、最終的に11要件・11テストになりました。
状態表は、pay/ship の8セルと cancel の4セル、計12セルを確認しています。

## 在庫を失わない条件と反例を先に用意する

「HTTP がエラーを返した」だけでは、在庫が元に戻ったか分かりません。
正常対照と、失敗後の内部状態を別に確認します。

| 条件 | 反例 | 検査内容 |
|---|---|---|
| 全商品を引き当てるか、何も変えない | 2商品目の失敗で1商品目だけ減る | 変更前後の全在庫と注文 |
| キャンセルは一度だけ在庫を戻す | 2回目にも在庫を加算する | 2回の応答と最終在庫 |
| 禁止状態を変更しない | 発送済み注文をキャンセルする | 409と状態・在庫の不変性 |
| 正常な注文は作成できる | 不正な注文も正常な注文も拒否する | 在庫10から3個引き当てて7になる対照 |

### 入力プロンプト: 障害を注入できる設計を検証する

```text
T2 として、状態変更と在庫ロールバックの設計を隔離した scratch で検証してください。
途中の引当・キャンセル処理へ、テスト用の障害を注入できるようにしてください。
失敗応答だけでなく、前後の在庫、引当済み数、注文状態を独立に比較してください。

HTTP テストは port 0 と起動完了通知を使い、固定 sleep へ依存しないでください。
時計は注入し、テストごとに独立したストアを用意してください。
認証の境界、在庫の原子性、状態遷移、テストの検出力を独立レビューしてください。
実測した前提と、レビューの指摘・処置を各機能の仕様へ反映してください。
```

今回の障害検査は、引当26ケースとキャンセル26ケースで行いました。
生成した商品の件数は1～4で、100件や整数上限は別の固定 fixture です。
この検査は、持続的な高負荷や複数プロセスでの共有在庫を保証するものではありません。

## 機能ごとに Red・Green・mutation を確認する

### 入力プロンプト: 依存順に実装する

```text
計画の依存順に、一機能ずつ進めてください。
仕様から期待結果を決め、正常対照とエラーのテストを先に書き、
期待した assertion Red を実際に確認してから実装してください。
import/setup の失敗は Red に使わないでください。

各機能で Green、独立レビュー、限定した mutation と元バイト列への復元を確認してください。
最後に npx musubix6 sdd gate --json と
npx musubix6 sdd diagnostics --profile javascript --json を実行してください。
ログは .experiment/evidence/、実際の結果と未確認は .experiment/result-native.json へ保存してください。
過去の失敗や、実装後に取り直した Red は消さず、当初の Red と区別してください。
```

今回も一直線に成功したわけではありません。
認証の検証用ヘルパーと、存在しない注文 ID の fixture に誤りがあり、Green や証跡の確認で失敗しました。
訂正後の再実行は、実装後の re-Red を含む履歴として保存しています。
すべてを「最初から正しい実装前 Red だった」とは説明していません。

ネイティブ工程の最終 gate と JavaScript 診断は PASS でした。
mutation は49種類で、再実行や re-Red を含む記録は65件あります。
この2つを同じ件数として合算してはいけません。
初期の一部の mutation 個別ログは同じ名前を再利用しており、すべてが当初から不変保存だったわけではありません。
この制限と、残っている集約ログ・ハッシュ履歴も記録しています。

## 実 HTTP で注文からキャンセルまで動かす

### 入力プロンプト: デモを作って実行する

```text
bin/server.mjs と、実際の別プロセスへ HTTP 接続する bin/demo.mjs を用意してください。
サーバーは既定で 127.0.0.1 へ bind し、デモでは port 0 を使ってください。
API_KEYS には tutorial-dummy-key-A など、16文字以上の公開ダミー値だけを使ってください。

health、認証失敗、商品登録、注文作成、支払、発送、キャンセルを順に実行してください。
商品 A は価格100・在庫10、最初の注文は3個にしてください。
最初の注文を発送した後の cancel は409です。
次に2個の注文を作成し、支払後にキャンセルしてください。
再キャンセルが409で、在庫が二重に戻らないことを確認してください。
最後に自分のサーバーを停止して再起動し、商品と注文が消えることも確認してください。
各応答と状態を assertion で比較し、途中失敗は非ゼロ終了にしてください。
```

今回の実 HTTP では、次の結果を確認しました。

| 段階 | 在庫 | 応答・状態 |
|---|---:|---|
| 商品登録 | 10 | 登録成功 |
| 3個の注文を作成 | 7 | `created` |
| 支払・発送 | 7 | `paid` → `shipped` |
| 発送済み注文をキャンセル | 7 | 409、在庫は戻らない |
| 次の2個の注文を作成 | 5 | 新しい注文を作成 |
| その注文を支払後にキャンセル | 7 | `cancelled`、2個だけ戻る |
| 同じ注文を再キャンセル | 7 | 409、在庫は増えない |

欠落・誤り・重複した API キーの拒否と、再起動後の空の状態も確認しています。
プロセスが終了コード0を返すだけでなく、デモ内の各 assertion と応答を確認しました。

## WSL コンテナーの API へホストから接続する

CLI だけの第1編と違い、今回は HTTP ポートを公開します。
コンテナー内の bind と、ホスト側の公開範囲は別の設定です。

### 入力プロンプト: loopback 限定で公開する

```text
wslc-containers を使い、node:24-alpine ベースの実行用・テスト用イメージを用意してください。
アプリ全テストを実際のコンテナーで実行し、実行数・成功数・skip・終了コードを記録してください。
開発用 npm ツールを実行イメージへ持ち込まないでください。

実行コンテナーでは HOST=0.0.0.0、PORT=3000 と公開ダミーの API_KEYS を明示してください。
ホスト側の公開は 127.0.0.1:<空いているポート>:3000 のみにしてください。
認証を外す、host network にする、ホストの全アドレスへ公開する変更はしないでください。

ホストから新しいサーバーへ、先ほどの在庫10→7→5→7と二重キャンセル拒否を再確認してください。
実際に作ったリソースの ID を記録し、それらだけを終了・削除してください。
作業用のコピーが gate の定義探索へ混ざらないよう管理し、
最後にネイティブの全体 gate と JavaScript 診断を再実行してください。
```

今回のコンテナー内テストは、コンテナー工程で追加した検査を含む13件がすべて成功しました。
skip は0件です。
ホスト側は `127.0.0.1:19373` で接続し、18段階の HTTP 操作と在庫の値を確認しました。
このポートは今回の実測値であり、読者の環境で空いている保証はありません。

最初に試したポートでは、Windows 側の予約・使用状況による `WSAEADDRINUSE` が発生しました。
WSL 内のソケット確認だけでは公開できると断定できません。
失敗した試行でコンテナーが作られていないことを確認し、別のポートで再試行しています。
集計器や後片づけの誤り、検証用プロセスを停止した終了コード137も失敗として残しました。
これらを正常終了へ読み替えていません。

## つまずきと対処・未確認の範囲

| 症状 | 原因・確認点 | 対処 |
|---|---|---|
| 認証が常に失敗する | `API_KEYS` の JSON 形式、キー、重複ヘッダー | 公開ダミー値と仕様の一致を確認する |
| 409なのに在庫が変わる | 状態検査前の更新や二重ロールバック | 応答だけでなく全状態の前後を比較する |
| ポートを公開できない | Windows 側も含むポート競合 | 作成状況を確認し、loopback の別ポートを選ぶ |
| コンテナー確認後に証跡の定義が変わる | 作業用コピーの `package.json` が探索へ入る | コピーの配置と定義差分を確認し、正規手順で再検証する |
| 再起動で注文が消える | この設計はメモリー上だけに保存する | 永続化済みと扱わず、別要件として設計する |

本番用の認証、TLS、RBAC、実決済、永続化、複数プロセスの共有在庫は対象外です。
HTTP の並行検査もペアでの操作が中心で、持続的な負荷試験ではありません。
キー比較の呼出しを観測したことは、タイミング攻撃への耐性を証明するものではありません。
