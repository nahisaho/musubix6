# Windows runner compatibility (#383, #384; v0.2.6 development)

Goal: repair the two native-Windows runner mechanisms without enabling an implicit shell or qualifying a new release platform.

| REQ | EARS requirement | Tests |
| --- | --- | --- |
| REQ-WINRUN-001 | When resolving a Windows command, the runner shall use case-insensitive PATH/PATHEXT names, consider supported .com/.exe/.bat/.cmd extensions in declared order, and avoid extensionless POSIX shims; POSIX resolution shall remain unchanged. | TEST-WINRUN-001 |
| REQ-WINRUN-002 | When a resolved Windows npm.cmd or npx.cmd has its standard adjacent node_modules/npm/bin entry point, the runner shall launch that entry point with the Node executable hosting SDD and the original argument vector, preserving output, exit and setup failure without invoking a shell; unsupported batch layouts shall fail explicitly. | TEST-WINRUN-002 |
| REQ-WINRUN-003 | When a command uses the Windows npm/npx adapter, command provenance shall bind the selected shim, actual Node interpreter, actual CLI script, selected npm lifecycle definitions and Windows SDK environment hashes; changes shall invalidate applicable evidence rather than reuse stale success. | TEST-WINRUN-003 |
| REQ-WINRUN-004 | When running on Windows, the runner shall inherit INCLUDE, LIB and LIBPATH case-insensitively with their exact values, while still excluding unrelated runner overrides; on other platforms these names shall not be added to the standard allowlist. | TEST-WINRUN-004 |

## Design
Keep the standalone zero-dependency sdd.mjs entry point. Share a resolved argv plan between execution and provenance; spawn with shell:false and windowsVerbatimArguments:false. Do not invoke cmd.exe, interpolate arguments, or execute arbitrary .cmd/.bat payloads. Recognize only npm.cmd/npx.cmd. Resolve the real shim path (following symlinks/junctions), then require a regular file at dirname(realShim)/node_modules/npm/bin/npm-cli.js or npx-cli.js respectively; bind both lexical and real shim/script locations. Other prefix/layout variants fail explicitly. Run with process.execPath: this deliberately uses SDD's Node runtime, not a possibly different adjacent node.exe or npm's dynamic prefix redirection. Missing CLI inputs and unsupported batch commands are explicit setup errors, never assertion Red.
Windows resolution reads the parent's effective case-insensitive PATH and PATHEXT; when duplicate casing exists, choose the lexicographically first key, matching Node child-env precedence. PATHEXT defaults to .COM;.EXE;.BAT;.CMD only when absent; split explicit values on semicolons, trim, case-fold and deduplicate, keeping only these four supported extensions. Empty/no-supported values produce no bare-name match. Use the reviewed PATH order; no implicit current-directory search is added. An explicitly named native .exe/.com does not require PATHEXT. The first resolved unsupported batch command is refused, not bypassed for a later executable. Unknown file associations are not executed.
Admit only the three named MSVC search-path variables on Windows. Inherit canonical uppercase keys with the same case-insensitive winner rule. Hash JSON.stringify(["sdd-msvc-env-v1",name,value-or-null]) for each canonical name into command definitions/admission; absent (null) and empty ("") differ. Never print raw SDK values. Retain the existing override blocklist and application-input mechanism. The native toolchain and its SDK paths remain trusted local inputs, not sandboxed or automatically installed.
Reuse existing npm command-closure handling for npm/npx, including explicit .cmd spellings: npm run/run-script/test/t, selected pre/post lifecycle scripts, existing project/ancestor/user/global .npmrc discovery and existing Node package-resolution metadata. Existing blocked inherited NODE_OPTIONS and NPM_CONFIG_* remain blocked, not newly admitted. Explicit reviewed argument/environment overrides keep their existing semantics. Do not claim arbitrary npm command semantics or undocumented .npmrc discovery beyond that existing boundary.
Keep the existing Linux release matrix and frozen 0.2.5 release artifacts untouched. Development tests and Windows CI controls do not establish Windows release qualification. No tag, publish, force push, or Issue closure based only on simulated Windows tests.

Risk stages (first violated condition): contract—unsupported batch layouts must be distinguished from supported npm; trusted inputs—PATH, actual CLI and admitted SDK values must remain bound; execution—no shell expansion and native process outcomes retained; verdict—setup failures cannot become assertion Red; evidence history—changed effective inputs stale existing evidence; integration/distribution—standalone/source/packed controls and separate native Windows checks. No stage is inapplicable.

Native npm and cl.exe positive controls are required before claiming native Windows verification; unavailable controls remain unknown.

## Assumptions and feasibility
The current host is Linux and has no cmd.exe, PowerShell, Wine or native MSVC available. Cross-platform injected runner tests do not establish native Windows execution. The initial #381 rerun failed prerequisite assertions because cargo was not on PATH; it is not regression Red evidence.
Feasibility spike: `node <session>/files/windows-runner-spike.mjs` passed on Linux/Node24: direct Node argv preserves spaces, metacharacters, embedded quotes and empty strings, with exits 0/7. This is not Windows quoting evidence. No policy change is implemented before human approval.
